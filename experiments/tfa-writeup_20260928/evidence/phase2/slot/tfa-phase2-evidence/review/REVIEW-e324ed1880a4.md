- Low-Medium: process.py:1211-1222. The timeout change applies to every run_process caller that passes readiness_path, not just the probe. It also changes the deadline for the non-readiness path. Base: the deadline was set right after spawn, readiness waited min(startup, remaining), and the total was bounded by timeout_seconds. Head, with readiness: the wait takes the full startup_timeout_seconds, and the deadline is reset afterwards, so the total is bounded by startup_timeout_seconds + timeout_seconds. For the probe's timeout scenario that means 0.3 s becomes up to 10.3 s. Head, without readiness: the deadline is `started + timeout_seconds`, where `started` (process.py:1142) comes before _spawn_contained. For Codex that spawn step now re-hashes the 488,879,584-byte launcher and the manifest, opens the launcher, and runs Popen, all counted against the execution budget. This narrowing is not disclosed. Today readiness_path has only test callers (grep over tfa/*.py), so production exposure is limited to the narrowing. The metadata still records only "timeout_seconds", which no longer describes the real wall-clock bound. No deterministic test pins either semantics: reverting to base would break no test except possibly the probe, flakily. Required change: say in the commit message that run_process semantics changed for all readiness callers and for the non-readiness deadline origin. Record the readiness timestamp and the deadline origin in metadata. Add a deterministic test for each case: readiness later than timeout_seconds but within the startup timeout does not time out, and post-readiness execution longer than timeout_seconds does time out.

- Low: process.py:360-372, 1017-1020. The post-launch check `/proc/<pid>/exe` is racy. By the time Popen returns, the launcher has exec'd. The launcher then execs META_EXEC_WRAPPER (a sealed memfd) and itself becomes the payload process. If the parent is descheduled, `exe` may already be the memfd, which raises "launched executable differs from its sealed identity" and kills the run. If the launcher exits quickly, the stat fails and raises a ProcessError instead of returning a normal result. The failure is fail-closed, but once a key becomes eligible it will make real-Codex runs flaky. The pinned descriptor is also never used as the exec target: execution still goes by path, so "opened launcher inode" is enforced only by that racy after-the-fact check. Required change: exec the pinned inode itself (pass_fds plus `/proc/self/fd/N`, or fexecve semantics), or treat the memfd wrapper as an accepted successor exe with evidence.
