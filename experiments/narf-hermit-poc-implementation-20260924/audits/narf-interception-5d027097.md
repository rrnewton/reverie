Cargo feature unification therefore compiles `syscall::__verification_clear_global`, `instruction::__verification_clear_instruction_interceptor`, and arch's CR4 reset into a boot-init kernel, contradicting the specifications and Cargo comments that production has no removal/replacement operation. `cargo tree -p narf-frame --features boot-init -e features` confirms `narf-userspace feature "verification-test-reset"` and its forwarded arch feature in the resolved production graph. A production caller can clear and replace either process-global interceptor. The instruction reset is especially incoherent on SMP: it clears the pointer and global request but clears CR4.TSD only on the calling CPU, so other CPUs may retain TSD and turn later user RDTSC into ordinary #GP after the interceptor is gone. Move reset enablement behind a feature that only `frame/kernel-test` selects, cfg-gate all cross-crate test bodies/imports that need it, and add a build/API check against the actual `narf-frame --features boot-init` graph, not merely narf-userspace's default-feature doctest.

- **S1 / blocking: `userspace/src/instruction.rs:98-113`, `userspace/src/user_task.rs:2614-2620`, `scheduler/src/stackful.rs:1975-1982` — successful publication is visible before interception is active on all CPUs, so a safe runtime installation can miss nondeterministic events.** `try_install_instruction_interceptor` first publishes the pointer with compare/exchange and only afterward raises the CR4.TSD request and updates the installing CPU. Other CPUs are updated lazily on a future first-entry or own-stack switch-in. A user task already running on another CPU can execute native RDTSC between publication and its next scheduler boundary, potentially indefinitely in a syscall-free loop. The public safe API and specification do not require installation before any user task becomes runnable, do not enforce such a boot phase, and do not rendezvous/IPI already-running CPUs. This violates the determinism purpose: even one unobserved timestamp cannot be repaired in the trace. Either enforce and document an installation-before-users invariant in the API/boot state, or quiesce user execution and arm every online CPU before reporting installation success; hotplug must join the same barrier. Add an SMP test with a continuously running user task on an AP, install from another CPU, and prove no post-success RDTSC escapes.

- **S1 / blocking: `userspace/src/instruction.rs:66-82,98-112,135-192` and `frame/src/x86_64/trap.rs:1421-1453` — subscription is mutable and evaluated twice per trap, making trap ownership and fail-closed behavior race with interceptor state.** `intercepts(&self, family)` is an unrestricted callback whose implementation may use interior-mutability state. Installation calls it once to decide whether to request CR4.TSD. The #GP handler then calls it through `instruction_interception_enabled`, and `dispatch_instruction` loads the global again and calls it a second time. If it is false at installation and later true, hardware trapping is never requested. If the first trap-time call returns true and the second returns false, exact RDTSC falls through as an ordinary synchronous fault instead of being emulated. Replacement/reset races can likewise make the two global loads disagree in verification builds. Nothing documents `intercepts` as immutable or pure, and tests do not count or perturb these calls. Capture an immutable family mask in the published slot, make the frame call one dispatch operation that makes one ownership decision, and use that same decision through entry/native/return; add stateful and concurrent tests proving one decision per trap.

- **S2 / major safety-contract gap: `userspace/src/instruction.rs:60-83,156-192` and `userspace/specification/spec.md:88-92` — a safe trait and safe dispatcher permit operations that violate the exception-context invariant.** The specification says instruction callbacks must not allocate, park, await, take a sleepable lock, or re-enter guest execution, while `frame/specification/spec.md:68-75` declares that a trap handler never allocates. Yet any safe `InstructionInterceptor` implementation can do all of those things, and `dispatch_instruction` has no per-CPU reentrancy guard. A backend mistake can therefore allocate or enter scheduler/guest machinery from a #GP handler with interrupts masked, potentially deadlocking or recursively corrupting exception state without crossing an unsafe boundary. Make the trait/installation contract explicitly unsafe with a `# Safety` section, add a per-CPU in-callback guard that fails closed on recursion, and keep the callable surface limited to preallocated lock-free/IRQ-safe operations. The same review should explicitly document syscall-callback locking/reentrancy separately because syscall context has different constraints.

- **S2 / evidence gap: `scheduler/src/stackful.rs:4761-4810`, `verification/src/lib.rs:3220-3452`, and `verification/src/lib.rs:2490-2729` — tests prove the local mechanisms but not AP migration, task identity, or the full documented lifecycle.** The live x86 test causally proves that current-CPU CR4.TSD traps ring-3 RDTSC and that syscall/RDTSC replacements reach user registers. The scheduler test, however, clears and reapplies TSD on the same CPU, runs a kernel-only future, and checks the CR4 cache rather than migrating a real user task to an AP and reading live CR4 there. The x86 int80 and AArch64 SVC tests issue their trap instructions from kernel mode. No test asserts `InstructionInvocation.task_id` for a scheduled/migrated guest, concurrent shared-state ordering, native `Continue` execution exactly once, mismatched result-family failure, opcode-copy failure, non-RDTSC #GP preservation, or syscall ptrace/signal/timer/reschedule ordering.
