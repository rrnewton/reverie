# Adversarial review: NARF syscall interception

Review target: `/home/newton/temp/agent_checkouts/narf-hermit-poc`, base `87b7cd1048a9492fccb4339558038c06d862e0b4` through exact head `70ed22719f190fb8362b0ff94015aa46d35a2518`.

## Findings

- **S1 / blocking — the public API does not enforce the advertised `Returned` versus `ContextManaged` state.** `userspace/src/syscall.rs:41-107` makes `TrapContext` fully mutating, including `set_return`, `set_rip`, both redirects, and signal-frame mutation. Both interceptor callbacks receive that raw mutable context (`userspace/src/syscall.rs:173-190`), outside the `InterceptCtx` that records native-handler calls. An entry callback can redirect the frame and return `Complete`; an exit callback can call `set_return` while returning `ContextManaged`, or redirect while returning `Returned`. In addition, an exit callback may directly convert an observed `ContextManaged` to `Returned`; `dispatch_intercepted` then only writes the return register (`userspace/src/syscall.rs:4901-4915`) and does not undo a parked task, restored state, RIP rewind, or kernel/user redirection. Thus the output enum is not the source of truth, and the documented claim at `userspace/src/syscall.rs:169-172` that this conversion can “resume with that value” is false for a redirected frame. This also contradicts the specification's claim that the layer cannot turn a context-managed path into a fabricated native completion (`userspace/specification/spec.md:43-46`). Make the dispatcher own the state transition: expose an observation/data-access view rather than an unrestricted `&mut dyn TrapContext`, allow result replacement only for an originally returned path, and keep `ContextManaged` immutable unless a separate suspension API can actually undo/complete the native context-management operation. Add negative tests in which callbacks attempt each forbidden cross-state mutation.

- **S1 / blocking — “one-shot” applies only to a table object, not to the published global identity.** `SyscallTable::install_interceptor` rejects a second interceptor in one local table (`userspace/src/syscall.rs:4837-4853`), but `install_global` unconditionally stores a new pointer (`userspace/src/syscall.rs:4733-4742`). A second publication therefore swaps every future dispatch to a different interceptor and leaks the previous table, directly violating `userspace/specification/spec.md:34-38`. The public `__test_clear_global` can also remove and free a published table (`userspace/src/syscall.rs:5292-5303`); its assertion that the atomic swap gives exclusive ownership is not true while a CPU that loaded the old pointer can still be dispatching through it. Publish with a null-to-pointer compare/exchange that rejects and returns the uninstalled table on failure. Restrict reset to an explicit test-only facility and use a quiescence/reclamation protocol (or deliberately leak test tables) before freeing. Tests must prove a second *global publication*, including a concurrent attempt, is rejected and that the original interceptor remains active; the existing test proves only duplicate installation on one unpublished table.

- **S1 / blocking — an intercepted unknown syscall bypasses the live x86-64 fast-path exit lifecycle.** In `kernel_syscall_entry_plain_with_state`, `None` dispatches the interceptor and returns immediately at `userspace/src/syscall.rs:3930-3933`. Known calls instead pass through the ptrace entry stop at `:3967-3976`, ptrace exit stop at `:4024-4035`, signal/timer delivery at `:4037-4063`, and exit reschedule at `:4064-4080`. Consequently, an interceptor that explicitly completes an unknown/version-probe syscall with a normal result receives behavior different from the same completion on a known syscall: no `PTRACE_SYSCALL` stops, no pending-signal delivery, and no reschedule check. The common `int 0x80`/AArch64 path does run its architecture-level signal hook after `kernel_syscall_entry` (`frame/src/x86_64/trap.rs:1156-1188`, `frame/src/aarch64/trap.rs:153-178`), so the two live entry mechanisms also disagree. Resolve `Option<Syscall>` only inside native dispatch and put interception inside a single outer entry/exit lifecycle for both known and unknown calls. Add a real x86-64 `syscall`-instruction test covering an unknown call completed by the interceptor while ptrace and a pending signal are active, plus parity coverage for `int 0x80` and AArch64 SVC.

- **S2 / major evidence gap — the new tests do not exercise the advertised live paths or several load-bearing contracts.** The host tests call a local `SyscallTable::dispatch` or the private `dispatch_intercepted` helper (`userspace/src/syscall.rs:5086-5156`). The kernel test does the same with another local table (`userspace/src/syscall.rs:5241-5287`); it never publishes that table, reaches `frame/src/x86_64/syscall.rs:369-405`, enters through `int 0x80` or AArch64 SVC, or composes with ptrace, I/O accounting, signals, and scheduling. No test constructs `SyscallInterception::Complete`, so native suppression and “at most once” are untested; there is also no versioned-call snapshot/fallback test, invocation RIP/RSP/task-identity assertion, concurrent shared-state test, or global one-shot test. The narrow QEMU test passes, but it proves only local dispatcher behavior, not the commit message's implied x86-64 path coverage. Add instrumented live-path acceptance tests and specify the required ordering (ptrace entry -> interceptor entry/native/exit -> ptrace exit -> signal/reschedule on the x86 fast path; I/O accounting and common-trap ordering as applicable) in `userspace/specification/spec.md`, then test both qualifying and violating cases.

## Execution-path assessment

- The intended first-class ownership and direct shared-state shape is present: an optional boxed `Send + Sync` interceptor is table-owned, callbacks are synchronous, and no IPC, ptrace, signal trampoline, binary rewrite, or polling transport was added.
- For known calls, both `kernel_syscall_entry` and `kernel_syscall_entry_plain_with_state` route through `dispatch_intercepted`. The common trap path places kernel-time and I/O accounting outside interception, and the I/O wrapper sees the final replaced return. The x86-64 `syscall` path places ptrace entry before interceptor entry and ptrace exit after interceptor exit/result replacement; signal delivery and rescheduling follow.
- Unknown calls reach interception and retain `-ENOSYS`/`InvalidOp` under `Continue`. Raw numbers retain version bits in `SyscallInvocation`, and unsupported versions intentionally fall through to v0 per `userspace/specification/spec.md:1169-1183`.
- The wrapper forwarding added for `IoAccountCtx` and `InterceptCtx` covers every current `TrapContext` method. That forwarding does not repair the outcome-state ambiguity described above.
