## Findings

### 1. MEDIUM — the publication fence spans arbitrary Tool prefix code, and neither `tool.rs` nor the PR body states the obligation that makes that safe. A Tool prefix that blocks on the parent now deadlocks, unbounded and undiagnosed.

`runtime.rs:3002` arms the fence. The callback is not constructed until `runtime.rs:3022-3026` and not polled until `runtime.rs:3031-3032`; `publish_after_fence` is at `runtime.rs:3033-3035`. So the interval during which a concurrent parent's `wait4`/`waitid(WNOHANG)` blocks in `waitability_pending()` (`executor.rs:1531-1564`, reached from `executor.rs:2978`) contains the **entire synchronous prefix of `on_backend_child_wait_event`**, which is arbitrary Tool code.

`PROPOSED-PR-BODY.md:13` describes this as "once logical publication is announced, a concurrent parent wait crosses only the bounded Ready-or-Failed bookkeeping transition." The preceding sentence does say the fence is armed "before polling the … prefix", so the two together are not contradictory — but "only the bounded … bookkeeping transition" understates the one operational fact a consumer implementer must know.

The concrete consequence is a new deadlock class:

* `tool.rs:207-212` requires the prefix to commit its decision **synchronously** — "it must not reach an `.await` first."
* `tool.rs:213-216` says the backend fences a concurrent parent across that prefix.
* Nothing says the prefix must also not **block**. At base this was safe: `vm.rs` (patch lines 4870-4877) published waitability *before* invoking the callback, so a prefix that blocked on the parent's `wait4` completing would make progress. At this head it cannot: the parent is parked on `ChildCompletionSlot::changed` with **no timeout** (`executor.rs:1548-1551`), so the run hangs with no typed backend failure and no terminal-deadlock report. Hermit's scheduler cannot see it either — the parent's host thread is blocked inside an injected syscall, so it never parks and `are_all_quiesced` never clears.

A related unstated obligation: `ProcessSignalControl::publish_child_exit` — which the doc tells a Tool to call from exactly that prefix — acquires the **parent's** `signal_transaction` (`process_signal_publication.rs:726`) plus the registry `failure` and `child_publications` mutexes. The trait doc states the "release your scheduler mutex first" rule only for `finish_publication_failure` and `finish_child_exit_publication_failure` (`process_signal_control.rs:6081-6095` in the patch), not for `publish_child_exit` itself.

**Impact.** `wait4(2)` specifies `WNOHANG` as "return immediately". The fence is the right analogue of Linux holding `tasklist_lock` across `do_notify_parent` + `wait_task_zombie`, but a kernel's hold is bounded by kernel code; here it is bounded by Tool code with no stated bound. For the intended Hermit consumer (decide under the scheduler mutex, wake, return) this is satisfiable and safe. For the published Reverie contract it is an undeclared deviation.

**Required correction.** In `tool.rs`, state that the synchronous prefix must neither `.await` nor block on parent progress, because the backend holds a concurrent parent wait across it; and note `publish_child_exit`'s parent-transaction lock-ordering obligation on that method. In `PROPOSED-PR-BODY.md`, replace "crosses only the bounded Ready-or-Failed bookkeeping transition" with wording that says the fence spans the Tool's synchronous prefix. **Recommended, not required:** bound `waitability_pending`'s condvar wait and convert a timeout into a typed backend failure, so a stuck prefix produces a diagnosis rather than a hang.

## Conclusion — determinism guarantee

**Sound for what this prerequisite claims. The specific host-timed input v4 demonstrated is now fenced and tested; the remaining one is correctly delegated and named.**

What is now a pure function of deterministic backend state, verified rather than assumed: the family snapshot (parent disposition, waitability, pending generation, full `ExitStatus`) is frozen once at the scheduler-ordered logical exit inside the exiting process's own transaction, with the parent's transaction held across the read (`executor.rs:4834-4865`, `process_signal_publication.rs:324-359`); `group_started` makes an `exit_group` the ordered transition while peer host handles are still being cancelled; both the Tool and Direct paths derive `ChildCompletion` from that snapshot rather than from the live `sigchld_auto_reap` atomic; the at-most-once ledger keyed on `(child tgid, child generation)` holds its guard across the whole mutation and readiness phase; `blocking_descendant`, the ancestry walk, and the two reported parents of `MultipleParents` are all `BTreeMap`-ordered; recipients are sorted. Child and direct-parent exits serialize on the direct parent's transaction, so **host retirement order cannot change the family outcome** — only guest-causal exit order can, which is declared.

The v4 blocker is closed. The interval between the callback prefix returning and waitability becoming visible no longer exists as an observable state: a concurrent `WNOHANG` either sees `Pending` (genuinely running, returns 0) or `PublicationFenced` (waits and then sees the authoritative result). There is no third answer, and the release-profile run confirms the barrier is not an artifact of debug codegen.

One host-timed boundary remains inside Reverie and is **not** closed by this patch: the gap between the child's scheduler-ordered logical exit (`record_process_exit`) and `begin_publication`, which happens later, at host worker-join time. During that gap a parent `WNOHANG` still returns 0. I traced the consumer: `config.backend_reports_physical_process_exits = backend == Backend::Sabre` (`consumer/hermit-cli/src/lib.rs:2410`), so on KVM the `WaitPhysicalChild` barrier is inert and Detcore's `handle_wait4` WNOHANG branch would inject the exact wait and spin on `yield_once()` (`consumer/detcore/src/syscalls/threads.rs:1632-1637`), whose retry count is host-timed. This is exactly what the consumer's two-stage Exit/callback fence must close — by *not* making the child ready in Detcore's shadow at the Exit hook, and instead making it ready in the Reverie callback prefix, at which point this patch's fence guarantees the parent cannot then observe "no child". The two halves compose correctly, and this patch is the necessary Reverie half. `PROPOSED-PR-BODY.md:17` states this boundary accurately.

This patch must **not** be credited with KVM determinism, backend parity, record/replay, or a complete child-exit repair. Hermit's synthetic plus-one-nanosecond child-exit timer (`primary/scheduler.rs:4202-4216`) and the `should_synthesize_child_exit_signal` / `signal_guest` numeric fallback (`scheduler.rs:1806-1808`, `:3023-3089`) are untouched, correctly.

## Conclusion — Linux and POSIX semantics

**Faithful on what it covers; the declared divergences are now complete except for one.**

Correct: `si_signo`/`si_code`/`si_pid`/`si_uid`/`si_status`/`si_utime`/`si_stime` at offsets 0/8/16/20/24/32/40 with 8-byte signed `clock_t`; `CLD_EXITED`/`CLD_KILLED`/`CLD_DUMPED` from `Exited`/`Signaled(_,false)`/`Signaled(_,true)` with an out-of-range exit code refused; explicit `SIG_IGN` suppressing generation and auto-reaping while `SA_NOCLDWAIT` auto-reaps but still generates — matching `do_notify_parent`; the frozen `waitable` predicate is the exact negation of the auto-reap predicate, so waitability and signal policy cannot drift; standard-signal coalescing retaining the first complete siginfo; `WNOWAIT` consuming nothing on either side of the boundary (backend `waitid` sets `consumed_child_wait` only when `WNOWAIT` is absent, patch lines 957-962; Detcore likewise, `threads.rs:465,1920,2084`); negative ticks refused; recipient selection by exact generation, live tasks only, mask-aware, sorted.

Making the SIGCHLD-generation and waitability decisions atomic from a concurrent waiter's point of view is now *closer* to Linux, not further: `do_notify_parent` and `wait_task_zombie` are serialized by `tasklist_lock`, and the fence is that serialization.

Declared divergences: fail-closed reparenting for a live or waitable descendant of a non-root process; auto-reap with no callback when the exact direct parent is already terminal; guest-causal root-versus-middle exit order changing teardown versus refusal; `SIG_DFL` transient-pending and later-handler-installation cases; `sigaction(SIGCHLD, SIG_IGN)` not flushing existing zombies; structurally zero `uid` and CPU times; no publication route for `Stopped`/`Continued`.

**Undeclared:** `WNOHANG` may block for the duration of arbitrary Tool code, and a Tool whose prefix blocks on parent progress deadlocks. That is finding 1, and it is the one Linux-semantics item that needs a sentence before landing.

## Residual risks

* Finding 1's deadlock class, and the absence of any timeout or diagnosis on `waitability_pending`.
* `family.terminal` and `child_publications` are never pruned: one entry per process generation for the life of the run. For a `make -jN`-scale tree this is unbounded growth plus an O(depth × live processes) validation walk under the `family` mutex on every non-root exit.
* `finish_child_exit_publication_failure` shares one `failure_forwarded` latch with `finish_publication_failure`, so the second acknowledgement of a different failure class is a silent `Ok(())`. Bounded by the run going terminal on the first.
* `register`'s duplicate guard is `debug_assert!`; in release a duplicate child generation would silently overwrite an edge. It relies on `TaskLifecycleTable` generation uniqueness, which is monotone (`elf.rs:163-176`).
* The `unreachable!` arms in `runtime.rs:3101-3120` and `vm.rs:4252-4269` are production panics whose soundness depends entirely on `process_family_exit`'s own match staying exhaustive.
* Scheduler-mutex inversion across `publish_child_exit`: I found no Reverie path that holds a process `signal_transaction` across a call into Tool code, but I cannot prove it exhaustively over a 1.5 MB `executor.rs`. The obligation is now load-bearing because `publish_child_exit` is an active production endpoint rather than an inactive one.
* `descriptor_retirement_accept_cleanup_releases_both_guards` will keep flaking the library gate until its nonblocking EOF read is retried or made blocking.
