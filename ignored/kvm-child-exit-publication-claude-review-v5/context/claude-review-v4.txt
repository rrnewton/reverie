## Findings

### 1. HIGH — blocker. The prefix-before-publish inversion creates an unfenced cross-thread window, and the packet's own retained log shows a parent's `wait4(WNOHANG)` losing that race. This is not a host-load artifact.

`candidate/reverie-kvm/src/runtime.rs:3021-3034`, against base `vm.rs` (patch lines 4546-4553).

Base ordering, which this PR removes:

```rust
*child_completion.lock()... = Some(completion);      // waitability FIRST
let _ = completion_notifier.send(raw_child_pid);
let caught = block_on(catch_owned_future_from(|| lifecycle_state.on_backend_child_wait_event(...)));
```

Head ordering:

```rust
let first_poll = poll_fn(|cx| Poll::Ready(callback.as_mut().poll(cx))).await;   // callback prefix FIRST
let waitability = if context.completion.publish(completion) { ... };            // waitability SECOND
```

The Tool's synchronous prefix is exactly where the fixture (and the documented contract, `tool.rs:206-218`) tells a Tool to act. In `tests/support/terminal_fork.rs:117-118` the prefix does `self.control.record("wait-event", ...)`, which notifies the condvar the parent is parked on (`terminal_fork.rs:208-217`). The parent then issues `wait4(child, WNOHANG)` on **its own host thread** while the child's host thread has returned from `poll` but has not yet reached `context.completion.publish(completion)`.

`ElfExecutor::execute_checked` → `synchronize_wait4` (`executor.rs:3081-3097`) → `collect_child_process(pid, false)` → `if !block && process.completion.is_pending() { return Ok(false) }` → `running = Some(pid)` → `WNOHANG` → `return Some(0)`. The parent observes "no child ready yet".

**This is exactly what the retained log records.** `qualification/terminal-fork-parallel-timeout.log:56-59`:

```
thread '<unnamed>' (797767) panicked at reverie-kvm/tests/support/terminal_fork.rs:226:21:
assertion `left == right` failed
  left: 0
 right: 2
```

`terminal_fork.rs:226` is `assert_eq!(guest.inject(wait).await?, i64::from(*child));`. Host TID **797767** is pid 1 of the failing mode-6 run — the failing test's own event list names it: `Event { kind: "start", pid: 1, value: 797767 }` (`terminal-fork-parallel-timeout.log:224`). The concurrently-running mode-2 case used TID 797757 and passed (`:99`), so the attribution is unambiguous.

The full causal chain, reconstructible from the log and consistent with every recorded event:

1. `:56` parent's `wait4(2, WNOHANG)` returns `0`; `assert_eq!` panics on TID 797767.
2. `:62,:67` same TID panics at `terminal_fork.rs:304:9` and `318:9` with `left: Exited(255)` — the parent's process status became 255 because its callback died. Those asserts precede the `record("thread-exit")` / `record("process-exit")` calls, which is why neither event appears.
3. `:224` events end `[..., wait-event 2, tool-drop 1]`, `parent_ready: false`.
4. `:223` the controller's 5-second `wait_timeout_while(!parent_ready)` fires.
5. `:226` the child's `wait_for` then hits `PoisonError` — poisoned by the controller's own assert at `473:5`, i.e. downstream.

**Impact.** The single test covering the new mode-6 path is flaky by construction, and the flakiness is a real ordering window this change introduced. More seriously, the window is a host-timed input that decides a guest-visible `wait4` return value, and the backend does not fence it: the parent and child run on different host threads with different `KvmBackend`s and therefore different entry gates, so `admit_ordinary_operation` does not serialize them. Nothing in `tool.rs:206-218` tells a Tool that waitability becomes visible strictly *after* its prefix returns; it says only that the Tool must commit its publication/suppression decision there — and the prompt's own boundary says "the same pinned future may await parent progress", i.e. a concurrent parent wait is expected.

Note the executor-yield reading does not rescue this: `poll_fn(|cx| Poll::Ready(...)).await` does not suspend, so the gap is a few instructions — but it is an **OS-thread preemption** window, which 23-way load reliably widens. Reordering statements cannot close it.

**Required correction.** One of:
(a) make the transition atomic from a concurrent waiter's point of view — arm a per-child readiness barrier before polling the prefix and release it in `publish`, so `collect_child_process` cannot report "still running" between prefix return and publication; or
(b) publish waitability before the prefix and give the Tool a separate suppression handle (this reverts the stated design goal, so (a) is preferable); or
(c) if the ordering is to stand, state in `tool.rs` that a Tool must not permit a concurrent parent wait between its prefix returning and the backend's publication, and fix the fixture to synchronise on publication rather than on the prefix record — but this narrows the delegated contract and must be stated in the PR description, not only in a comment.

In every case, `QUALIFICATION.md:15` must be corrected: it attributes the failure to "one `cancellation_preserves_status_across_child_wait_callback_panic` controller timeout at 5.00s under 23-way host load" and never mentions the `left: 0, right: 2` assertion that actually failed. The raw log was honestly retained — the note explicitly invites this scrutiny — but the characterisation is wrong, and the serialized rerun does not resolve the defect, it only re-runs the winning interleaving.

### 2. MEDIUM — a terminal *transitive* ancestor silently strips waitability from a child whose **direct parent is still live**, so that parent's `wait4` returns `ECHILD` instead of the status. Regression against base, untested.

`candidate/reverie-kvm/src/process_signal_publication.rs` (`has_terminal_ancestor`, patch lines 1202-1231; `RunTeardownChild` branch, patch lines 1440-1460), with `executor.rs:2763-2775`.

`ancestor_is_terminal = family.has_terminal_ancestor(process_key(parent))` walks the *whole* ancestry. So for R → C → G:

- If R is terminal and **C is still live**, G's exit takes `RunTeardownChild`.
- `runtime.rs:3064-3066` publishes `ChildCompletion::AutoReaped(family_status)`.
- `record_child_completion`'s `AutoReaped` arm is `Ok(())` — it does **not** insert into `state.children` (`executor.rs:2773`).
- No `on_backend_child_wait_event` is emitted.
- C's subsequent `wait4(G)` therefore falls through `synchronize_wait4` and returns `ECHILD`.

At base this could not happen: the Tool fork path computed `waitable` from the **direct parent's** live `sigchld_auto_reap` (`auto_reap = executor.child_exit_policy()`, patch line 4494), so G would have been `Waitable` and C's wait would have succeeded.

Reachability is narrow but real. Every *non-root* process that exits with a live descendant fails closed (`DescendantReparentingUnsupported`), so the only ways to get "terminal ancestor above a live intermediate" are (i) the **root** exiting — `is_root` is checked first and does **not** fail closed — or (ii) `record_process_failure`, which is already a run-failure path. Case (i) is the shape `terminal_fork` modes 0/1 exercise at two levels; at three levels with a live, waiting middle parent it is untested.

The prompt's stated intent says teardown should "suppress **dead-family** callbacks". Here the family is not dead — only the root is. That gap should either be closed (walk only until a live ancestor, or keep waitability for a live direct parent) or stated explicitly as a declared divergence.

**Required correction.** Add the permutation as a test (R terminal, C live and waiting, G exits) and either preserve C's waitability or record the divergence in the PR description alongside the F3 compatibility cost.

## Conclusion — determinism guarantee

**Not sound at this head. One host-timed input is unfenced and observable.**

What *is* now a pure function of deterministic backend state, and I verified it: the family snapshot (parent disposition, waitability, pending generation, full `ExitStatus`) is frozen once at the logical exit transition inside the exiting process's own transaction (`executor.rs:4725-4758`), with the parent's transaction held across the read; `group_started` makes an `exit_group` the ordered transition while peer host handles are still being cancelled; both the Tool and Direct paths derive `ChildCompletion` from that snapshot rather than from the live `sigchld_auto_reap` atomic at host join; the at-most-once ledger keyed on `(child tgid, child generation)` holds its guard across the whole mutation and readiness phase; `blocking_descendant`, `has_terminal_ancestor`'s parent walk, and `MultipleParents`' two reported parents are all `BTreeMap`-ordered, so no host order leaks; recipients are sorted. Lock ordering with the new `family` mutex is consistent — `family` is always innermost under the parent transaction in both `record_process_exit` and `publish`, and no path holds `family` while acquiring a transaction.

But per Axis 1 item 1, every host-timed input must stop influencing guest-visible ordering. The interval between the callback prefix returning and `ChildCompletionSlot::publish` does not: a concurrently running parent's `wait4(WNOHANG)` returns `0` inside it and the child's pid outside it. That is a guest-visible value decided by OS-thread preemption, and the packet's own log records it happening. Under Hermit's deterministic scheduler the parent would normally be parked, so this may not manifest for that one consumer — but Reverie's documented contract does not forbid a concurrent parent wait, the fixture models one deliberately, and the backend supplies no fence. Per Axis 1 item 3 (one defined transition per target state) and the skill's rule that a design argument is insufficient unless the code implements the claimed ordering, this axis is unresolved.

Finding 2 is a second, smaller determinism-adjacent issue: it is deterministic within a schedule, but it makes the *set* of waitable children depend on which ancestor became terminal, in a way base did not.

This patch must **not** be credited with KVM determinism, backend parity, record/replay, or a complete child-exit repair. Hermit's synthetic plus-one-nanosecond child-exit timer (`primary/scheduler.rs:4202-4216`) and the `should_synthesize_child_exit_signal` / `signal_guest` numeric fallback (`scheduler.rs:1806-1808`, `:3023-3089`) are untouched, correctly. There is still no production `publish_child_exit` caller outside tests and fixtures.

## Conclusion — Linux and POSIX semantics

**Faithful on what it covers; five named divergences, four of them declared.**

Correct: `si_signo`/`si_code`/`si_pid`/`si_uid`/`si_status`/`si_utime`/`si_stime` at offsets 0/8/16/20/24/32/40 with 8-byte signed `clock_t`, matching the x86-64 SIGCHLD `siginfo_t`; `CLD_EXITED`/`CLD_KILLED`/`CLD_DUMPED` derived from `Exited`/`Signaled(_,false)`/`Signaled(_,true)` with an out-of-range exit code refused; explicit `SIG_IGN` suppressing generation and auto-reaping while `SA_NOCLDWAIT` auto-reaps but still generates — exactly `do_notify_parent`; the frozen `waitable` predicate is the negation of `sigchld_auto_reaps`, so waitability and signal policy cannot drift; standard-signal coalescing retaining the first complete siginfo; `WNOWAIT` consuming nothing on either side of the boundary; negative ticks refused; recipient selection by exact generation, live tasks only, mask-aware, sorted.

Divergent: the SIGCHLD-before-waitability non-atomicity, which Linux's `do_notify_parent` performs under `tasklist_lock` — now not merely theoretical but observed (finding 1); a live direct parent's child becoming unreapable under a terminal transitive ancestor (finding 2, **undeclared**); `SIG_DFL` transient-pending and later-handler cases; `sigaction(SIGCHLD, SIG_IGN)` not flushing existing zombies; `uid` and CPU times structurally zero; no publication route for `Stopped`/`Continued`.

The fail-closed reparenting boundary is not Linux behaviour and is not claimed to be. Converting "silently wrong" into "loudly refused" is right for this stage; the asymmetry (root-versus-middle exit order changes teardown versus refusal) is now correctly tested and commented, and belongs in the PR description.

## Residual risks

- Finding 3's `Drop`-as-last-removal path is unguarded and untested.
- `finish_child_exit_publication_failure` does not clear `registry.failure`, and `failure_forwarded` is one registry-wide latch, so a second acknowledgement is a silent `Ok(())`. Bounded: only one failure can be retained, because the first latches the run terminal.
- `debug_assert!(previous.is_none())` guards every ledger insert and `register`'s duplicate check; in release a duplicate would silently overwrite. The `child_publications` guard is held across check-and-insert so that one is unreachable; `register`'s relies on the shared `TaskLifecycleTable` making `process_generation` globally unique.
- `ChildCompletionSlot::publish`/`fail_if_pending`/`is_pending` panic on a poisoned lock while `take()` maps poison to a typed `Poisoned`. Asymmetric; pre-existing pattern.
- The `unreachable!` arms in `runtime.rs:3087-3106` and `vm.rs:4428-4445` are production panics guarded only by `process_family_exit`'s own match. Structurally sound today; brittle to a future variant.
- `has_terminal_ancestor` is now on the critical path of every non-root exit, O(depth × live processes) under the `family` mutex. For a `make -jN`-scale tree this is O(depth · P²) over a run.
- `family.terminal` and `child_publications` grow one entry per process generation for the life of the run, unpruned.
- Scheduler-mutex inversion across `publish_child_exit` (consumer holds its scheduler mutex; Reverie acquires the parent's process transaction) — I found no backend path holding a process `signal_transaction` across a call into the Tool, but I cannot prove it exhaustively over a 1.5 MB `executor.rs`.
