## Findings

### 1. Medium (blocker for this prerequisite) — the Direct and Tool paths do *not* enforce the same frozen result: one hard-checks status agreement, the other only `debug_assert`s it

`candidate/reverie-kvm/src/vm.rs:2254-2263` versus `candidate/reverie-kvm/src/runtime.rs:2955-2961`

Direct path:

```rust
if snapshot.completion.status != status {
    return Err(Error::UnexpectedVcpuExit(format!(
        "KVM fork child {} family status disagrees with its process status", child.pid)));
}
let completion = ChildCompletion::from_waitability(snapshot.completion.status, snapshot.completion.waitable);
```

Tool path:

```rust
debug_assert_eq!(snapshot.completion.child, context.child);
debug_assert_eq!(snapshot.completion.status, status);
let completion = ChildCompletion::from_waitability(snapshot.completion.status, snapshot.completion.waitable);
```

In a release build both `debug_assert_eq!`s vanish. The two values can legitimately differ: `status` at `runtime.rs:2920-2944` is taken from `cancelled_exit`, or from `outcome`, and only replaced by `executor.process_exit_status()` when `pid == tid && natural_exit`. The `child_wait` arm is gated on `outcome.is_ok() && workers.is_ok() && process_status.is_ok()` (`runtime.rs:2945-2948`), which a **cancelled** child satisfies with `natural_exit == false`. On that path `status` never comes from the lifecycle table that produced the snapshot.

**Impact.** The parent's `waitpid` would report `snapshot.completion.status` (recorded into `state.children` through `record_child_completion`) while the Tool's `on_exit` hook and the returned tuple carry a different `status`. That is a silent, guest-visible inconsistency in release, produced by this change's own new code, in exactly the mechanism the change exists to make authoritative. The `terminal_fork` suite exercises the cancellation path (modes 2 and 6) only under `cargo test`, i.e. debug — so the tests would have caught a divergence, but they do not protect release.

The same asymmetry appears one branch up: the Direct path **refuses** `RunTeardownChild` (`vm.rs:2235-2240`) while the Tool path **accepts and auto-reaps** it (`runtime.rs:3012-3028`). That may be justified — the Direct path's parent is on the caller's own stack and cannot be terminal unless an ancestor is — but it is not stated anywhere, and the prompt's own criterion is "Direct and Tool paths enforce the same frozen result".

**Required correction.** Promote the Tool path's `debug_assert_eq!(snapshot.completion.status, status)` (and the `child` equality) to a hard `Err`, matching `vm.rs:2254-2258`. Either unify the `RunTeardownChild` disposition across the two paths or state, in a comment at `vm.rs:2235`, why the nested Direct fork cannot reach it.

### 2. Medium — the managed wait/ledger mismatch and the ancestry invariant fail closed by production `assert!` panic, not by a typed error, inside guest syscall dispatch

`candidate/reverie-kvm/src/executor.rs:4326-4334`, `:4866-4869`; `candidate/reverie-kvm/src/process_signal_publication.rs:123-126`, `:138-141`

```rust
fn record_consumed_child_wait(&self, child_pid: i32) {
    let parent = self.admitted_signal_identity().process;
    let consumed = self.signal_registry.consume_child_wait(parent, child_pid);
    assert!(
        consumed || !self.signal_registry.controlled(),
        "a Tool-controlled KVM wait reaped child {child_pid} without a waitable exact family entry"
    );
}
```

and, at the top of `SyscallExecutor::execute`:

```rust
assert!(self.state.consumed_child_wait.is_none(),
    "a KVM child-wait ledger effect must be consumed by its originating syscall");
```

and in the ancestry walk:

```rust
assert!(visited.insert(ancestor), "KVM process-family ancestry must remain acyclic");
assert!(parents.next().is_none(), "one KVM process generation cannot have multiple family parents");
```

These are plain `assert!`, live in release. Every *other* fail-closed boundary this change introduces is a typed `crate::Error` a consumer can match: `DescendantReparentingUnsupported`, `ParentGenerationUnavailable`, `ParentChildRelationUnavailable`, `ChildExitPublication` (`error.rs:132-186`). The mismatch case is the one the prompt names as required behavior ("A managed mismatch fails closed"), so it deserves the same typed treatment.

`record_consumed_child_wait` is reached from `SyscallExecutor::execute`, i.e. from inside `Guest::inject`. A panic there unwinds through whichever `catch_unwind` happens to enclose the poll — the Tool-panic machinery for an injected syscall, or the vm worker otherwise — and is reported as a *guest/Tool panic* rather than as a backend family-invariant violation. The consequence is fail-closed in effect, but mislabeled and unmatched.

I could not construct a reachable path for either ancestry `assert!`: `state.task_lifecycle` is one shared `Arc` across the whole process tree (`elf.rs:867`), so `process_generation` is globally unique and a duplicate or second-parent key cannot be produced by `register` (`process_signal_publication.rs:198-210`). They are defensive. They should still be `debug_assert!` or a typed refusal, not a release panic in the exit path.

**Required correction.** Return a typed `crate::Error` (a new `FamilyWaitLedgerMismatch { parent, child }` or similar) from the wait path instead of panicking, and demote the two ancestry `assert!`s to `debug_assert!` or make them yield the existing `ParentChildRelationUnavailable` shape.

### 3. Medium — the terminal-ancestor rule closes the *transitivity* hole but does not close the order-sensitivity; the flip that decides abort-vs-success is the one permutation no test pins

`candidate/reverie-kvm/src/process_signal_publication.rs:333-352`

```rust
let ancestor_is_terminal =
    parent_identity.is_some_and(|parent| family.has_terminal_ancestor(process_key(parent)));
let exit = if is_root { Root }
    else if ancestor_is_terminal { /* remove edge */ RunTeardownChild { status } }
    else if let Some(child) = blocking_descendant { DescendantReparentingUnsupported { child } }
```

**What genuinely improved over `d794a5e3`.** The predicate is now transitive (`has_terminal_ancestor`, `:120-144`) rather than "my immediate parent is terminal", the teardown branch removes its exact edge (`:341-349`), and `terminal_ancestor_consumes_nested_family_in_either_descendant_order` (`:2807-2865`) exercises root→child→grandchild and root→grandchild→child, asserting `direct_children.is_empty()` afterwards. I traced the edge bookkeeping and could not find a way for a *non-terminal* process to lose its incoming edge: every removal site (`record_process_exit` teardown branch, the `waitable == false` auto-reap branch, `record_process_failure` `:249-257`, `consume_child_wait` `:417-434`) coincides with a `terminal` insert or requires an already-terminal `WaitableZombie`. So the walk cannot terminate early and mis-classify. That was a real hole and it is closed.

**What did not change.** The branch order is still ancestor-teardown before descendant refusal, so for root `R` → child `C` → grandchild `G` where `C` never reaps `G`:

- `C` exits while `R` is alive → `blocking_descendant` fires → `Error::DescendantReparentingUnsupported` → **run aborts** (real-KVM matrix modes 0 and 1, `tests/static_elf.rs` grandchild matrix; four diagnostics in `qualification/real-grandchild.log:5-8`).
- `R` exits first → `terminal[R] = Root` → `C` then `G` are both `RunTeardownChild` → **run succeeds** (`terminal_ancestor_consumes_nested_family_in_either_descendant_order`).

Both halves are tested; no test asserts they *agree*, because they do not. `terminal_ancestor_consumes_nested_family_in_either_descendant_order` retires the root **first in both branches** (`:2812-2818`) and varies only the descendant order after that, so the decisive permutation — middle-exits-first versus root-exits-first — is covered by two separate tests with two opposite verdicts and no cross-reference.

**Is that merely relabelling?** No, and I want to say so precisely, because it is the closest call in this review. The rule now maps onto a real Linux distinction: reparenting `G` to a *live* namespace init is unimplemented and refused, while a dead namespace init means the whole container is tearing down. That is a defensible product rule, not a renamed failure. But two consequences remain and should be recorded rather than left implicit:

1. Under chaos mode or `hermit analyze` schedule search, root-vs-middle exit order is a scheduling choice for a guest that does not synchronize (`sh -c '(cmd &)'`, a daemonizing child, out-of-order `make` reaping). A seed change can turn a passing run into a hard abort. Within one schedule the verdict is a deterministic function of guest-causal state, so this is not a determinism violation — it is a compatibility and schedule-search usability cost against `PROJECT_VISION.md`'s "Fully runs all hermit `--strict --verify` that ptrace can".
2. In the teardown-absorbed direction the descendants **keep executing to completion** after the container root has exited, where Linux kills every task in the namespace when PID 1 exits. That is pre-existing (base also ran them to completion) but the new rule now silently absorbs their exits instead of reporting them.

**Required correction.** Add the missing permutation as an explicit test (`R` live + `C` exits with unreaped `G` → error; `R` terminal first + same guest → teardown) in one test that names the asymmetry, and state the compatibility cost in the PR description, not only in the code comment at `:337-340`.

### 4. Low — the Tool is handed the SIGCHLD publication point *before* waitability, which Linux makes atomic, and the trait doc does not name the consequence

`candidate/reverie-kvm/src/runtime.rs:2977-2997`, `candidate/reverie/src/tool.rs:206-218`

```rust
let first_poll = poll_fn(|cx| Poll::Ready(callback.as_mut().poll(cx))).await;
let waitability = if context.completion.publish(completion) { notify } else { error };
```

The Tool's synchronous prefix — where it is told to commit its publish/suppress decision — runs before `context.completion.publish(...)` and before the parent's `record_child_completion` inserts the child into `state.children`. So a Tool that calls `publish_child_exit` in that prefix (exactly what the real-KVM fixture does, `tests/static_elf.rs` `on_backend_child_wait_event`) makes SIGCHLD pending while the child is not yet waitable. Linux's `do_notify_parent` sets the zombie waitable and generates SIGCHLD under `tasklist_lock`; a handler that immediately calls `waitpid(WNOHANG)` is guaranteed to find the child.

The real-KVM test passes because its guest is parked in a blocking `waitpid(-1)` with `SA_RESTART`, which retries. A guest whose SIGCHLD handler does a single `waitpid(WNOHANG)` and treats `0`/`ECHILD` as "nothing there" could observe the window. The doc at `tool.rs:206-213` specifies the ordering but does not state that the Tool therefore owns the atomicity fence.

Note the ordering is not gratuitous: `waitable` is already frozen in the snapshot, so the prefix does not decide auto-reap; it exists so a deterministic consumer can order the SIGCHLD relative to its own scheduler state. That is the right delegation — it just needs saying.

### 5. Low — `uid`, `user_ticks`, `system_ticks` are still structurally unable to be nonzero (prior finding 8, unchanged)

`candidate/reverie-kvm/src/process_signal_publication.rs:354-362` hardcodes `uid: 0, user_ticks: 0, system_ticks: 0`, and `publish` requires exact snapshot equality (`:669-678`), so a Tool cannot supply real values. Nonzero encoding is exercised only by the pure encoder test `child_siginfo_encoder_and_coalescing_retain_first_nonzero_metadata`. Internally consistent (`waitid` writes `si_uid = 0`, `si_utime = 0`, `si_stime = 0` at `executor.rs:15448-15452`; `wait4` zeroes `rusage`) and uid 0 matches the paper's container mapping (§5.5). Three newly-public fields that read as live plumbing but cannot be.

### 6. Low — a `SIG_DFL` SIGCHLD is still enqueued, and installing a handler over `SIG_DFL` after child exit still yields a delivery Linux would have discarded (prior finding 9, unchanged)

`process_signal_publication.rs:724-738` short-circuits only on `disposition == PublicationDisposition::Ignored`; `KernelSigaction::is_ignored()` is exactly `handler == SIG_IGN` (`signal.rs:188-190`). `discards_pending` (`executor.rs:14720-14724`) bumps the pending generation for `SIG_IGN` and for `SIG_DFL` on a default-ignored signal — but **not** for installing a handler. So:

- `SIG_DFL` + unblocked at child exit → KVM enqueues; Linux's `sig_ignored()` discards. The guest can see a transient `sigpending()` bit and spurious signalfd readiness.
- `SIG_DFL` at exit, handler installed before publication → generation unchanged → `Queued` → delivered. Linux discarded that instance at generation time.

Both are unexercised: the grandchild matrix blocks SIGCHLD throughout (`sigprocmask(SIG_BLOCK, SIGCHLD)`), and Linux *does* queue a blocked `SIG_DFL` SIGCHLD, so that case is faithful.

## Conclusion — determinism guarantee

**Sound within a schedule; the one remaining order-dependence is a compatibility cost, not a determinism violation.**

What is now a pure function of deterministic backend state: the family snapshot (parent disposition, waitability, pending generation, full `ExitStatus`) is frozen once at the *logical* exit transition inside the exiting process's own transaction (`executor.rs:4715-4757`), and both the Tool path and the Direct path derive `ChildCompletion` from it rather than from the live `sigchld_auto_reap` atomic at host join. `group_started` (`elf.rs:254-279`) makes an `exit_group` the ordered transition while peer host handles are still being cancelled, and `group_exit_records_family_order_before_peer_host_retirement` exercises both peer-retirement orders against both auto-reap dispositions. The at-most-once ledger keyed on `(child tgid, child generation)` removes the coalesce-then-dequeue duplicate, holding its guard across the whole mutation and readiness phase (`:701-711`, `:825-843`). Recipients are sorted. The `waitid` selection rule now exists in exactly one place and the ledger consumes the pid the backend actually removed.

Lock ordering: I traced it again against the new `family` mutex and found no inversion and no cycle. `register` takes `family` then releases it before `processes`; every reader (`record_process_exit`, `record_process_failure`) calls `lookup` — whose `processes` guard is a statement-scoped temporary — before acquiring `family`. `record_process_exit` releases the parent's lifecycle and signals guards inside its closure before taking `family` (`:290-321`), and `publish` releases `family` (via `process_family_exit`) before taking `failure` → `child_publications` → process `signals`. The ancestry walk is provably acyclic because one shared `TaskLifecycleTable` (`elf.rs:867`) makes `process_generation` globally unique.

Host-timed inputs that remain the consumer's to fence, as `process_signal_control.rs:198-199` states: `set_signalfd_ready` is real host I/O whose failure latches the run terminal; the interval between the frozen snapshot and the publication (disposition and pending generation frozen, so a late ignore yields `DiscardedByDispositionChange` rather than a race — but a late *handler installation* over `SIG_DFL` still gets a delivery Linux would not produce, finding 6); and the SIGCHLD-before-waitability window in finding 4.

This patch must **not** be credited with KVM determinism, backend parity, record/replay, or a complete child-exit repair. Hermit's synthetic plus-one-nanosecond child-exit timer (`primary/scheduler.rs:4202-4216`) and the `should_synthesize_child_exit_signal` / `signal_guest` numeric fallback (`scheduler.rs:1806-1808`, `3023-3089`) are untouched, as they should be. There is still no production `publish_child_exit` caller outside tests and fixtures.

## Conclusion — Linux and POSIX semantics

**Faithful on what it covers; four named divergences, all declared.**

Correct: `si_signo`/`si_code`/`si_pid`/`si_uid`/`si_status`/`si_utime`/`si_stime` at offsets 0/8/16/20/24/32/40 with 8-byte signed `clock_t`, matching the x86-64 SIGCHLD `siginfo_t`; `CLD_EXITED`/`CLD_KILLED`/`CLD_DUMPED` from `Exited`/`Signaled(_,false)`/`Signaled(_,true)` with an out-of-range exit code refused; explicit `SIG_IGN` suppressing generation and auto-reaping while `SA_NOCLDWAIT` auto-reaps but still generates — exactly `do_notify_parent`, and the frozen `waitable` predicate (`:316`) is the negation of `sigchld_auto_reaps` (`executor.rs:15212-15216`), so waitability and signal policy cannot drift; standard-signal coalescing retaining the first complete siginfo; `WNOWAIT` consuming nothing on either side of the boundary; negative ticks refused; recipient selection by exact generation, live tasks only, mask-aware, sorted.

Divergent or absent: the `SIG_DFL` transient-pending and later-handler cases (finding 6); `sigaction(SIGCHLD, SIG_IGN)` not flushing *existing* zombies (base resampled and was also wrong; head is deterministically wrong, which is the right trade at this stage); `uid` and CPU times structurally zero (finding 5); no publication route for `Stopped`/`Continued`; SIGCHLD-before-waitability non-atomicity (finding 4).

Separately, the fail-closed reparenting boundary is not Linux behaviour and is not claimed to be — Linux reparents to the nearest subreaper or init, and namespace PID 1's exit kills the namespace. Converting "silently wrong" into "loudly refused" is right for this stage, but it narrows the envelope against `PROJECT_VISION.md`, and the narrowing is now *asymmetric* (finding 3). That cost belongs in the PR description.

## Residual risks

- **`(None, true) if pid == tid` at `runtime.rs:3052-3055`** calls `process_family_exit()` for a non-fork leader and converts a missing terminal entry into `UnexpectedVcpuExit("lost its terminal family transition")`. The guard admits a *cancelled* root (`natural_exit == false` leaves `process_status = Ok(())`), where `take_exit` may never have recorded a transition. `terminal_fork` modes 2 and 6 cancel and pass, and those runs error for other reasons anyway, so I could not demonstrate it — but a successful cancelling run would be a new spurious fatal.
- **Scheduler-mutex inversion.** `publish_child_exit` acquires the parent process's transaction while the consumer holds its scheduler mutex. I found no backend path holding a process `signal_transaction` across a call into the Tool (`fork_child`, `thread_child`, `take_exit`, `retire_failed_thread`, `replace_after_exec` and `Drop` all hold it without calling the Tool, and `on_backend_child_wait_event` is invoked with no publication guard held), but I cannot prove it exhaustively over a 1.5 MB `executor.rs`. Pre-dates this change via the alarm path.
- `finish_child_exit_publication_failure` does not clear `registry.failure`, and `failure_forwarded` is one registry-wide latch (`:997-999`), so a second acknowledgement is a silent `Ok(())`. Bounded: only one failure can be retained, because the first latches the run terminal.
- `debug_assert!(previous.is_none())` guards every ledger insert and the `register` duplicate check; in release a duplicate would silently overwrite. Consequences are fail-closed (`InvalidCompletion` at `publish`), and the shared lifecycle table makes duplicates unreachable.
- `ChildExitCompletion` is `Copy + Serialize + Deserialize`, so a receipt is freely clonable; the only binding of an acknowledgement to one operation is exact equality, which is tested including the near miss.
