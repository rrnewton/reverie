## Findings

No high- or medium-severity correctness defect found in the sealed-carrier mechanism, the open-path ordering, or the fdinfo lifecycle. Five low/informational findings follow.

**1. Low — stale `synthetic_proc_nofollow_fds` cleanup covers only one of the descriptor allocators.**
`candidate/reverie-kvm/src/executor.rs:13195-13199` clears the stale marker only when `open_synthetic_proc` allocates. Every other allocator leaves it untouched: `insert_file_with_flags` (`executor.rs:7815-7846`), which backs `open_guest_fd_path` (`7522`), `open_virtual_file`, and pipe/socket creation; and `install_received_rights` (`executor.rs:10514-10521`), which explicitly does `proc_files.insert`/`remove` for the received fd but never touches the nofollow set. The `F_GETFL` overlay at `executor.rs:13570-13580` consults the set for *any* guest fd, not only proc carriers, so a stale entry would add a spurious `O_NOFOLLOW` to an unrelated description. Guest-visible impact if reachable: wrong `fcntl(F_GETFL)` for an arbitrary descriptor — deterministic, but wrong. I could **not** construct a reachable stale entry at this head: `close` (`13712-13717`), both `duplicate_fd` paths (`8079-8086`, `8100-8107`), `duplicate_fd_at_or_above` (`7980-7986`), and the exec filter (`elf.rs:1071-1075`) all clear or filter it, and `insert_file_with_flags` only selects vacant fds. Required correction: move the `remove` into `insert_file_with_flags` so every allocation path is covered, or state in the PR that the side table is consulted only for fds the synthetic-proc allocator owns. Not blocking.

**2. Low — the new host-kernel dependence of guest-visible errno is not in the disclosed residual list.**
`elf.rs:67-138` probes the host once and caches it; `executor.rs:7040-7046`, `212-227`, `2038-2046`, `7062-7078` then make the guest's errno for `O_CREAT|O_DIRECTORY` (`EINVAL` vs `ENOTDIR`/`EEXIST`) and for `/proc/.../fdinfo/` (`EINVAL` vs `EISDIR`) a function of the supervisor's kernel version. This is the only way to match native behavior, and the PR body says the policy is cached, but it is a genuinely new cross-host divergence surface: the same guest program yields different errnos on a 6.3 host and a 7.1 host. The PR's residual section otherwise enumerates nonclaims carefully and omits this one. Required correction: add it to the disclosed residuals. No code change needed (record/replay is explicitly out of scope).

**3. Low — a transient probe failure is cached permanently.**
`elf.rs:41-43` declares `OnceLock<Result<RegularCreateDirectoryPolicy, String>>` and `elf.rs:131` uses `get_or_init`, so an `Err` is stored forever. A single failure of `openat`/`fstat`/`fstatfs` on `/proc/self/status` — including exhausting `POLICY_OPEN_EINTR_ATTEMPTS = 16` at `elf.rs:31,49-64` — permanently disables every later `load_static_elf`/`load_static_elf_file` in the same supervisor process. It fails closed, and procfs `openat` is not realistically `EINTR`-interruptible, so this is near-unreachable; caching the failure is also arguably the right choice for determinism (the policy must not change mid-run). Required correction: state the permanent-poison behavior in a comment, or cache success only. Not blocking.

**4. Low — dead `/proc/uptime` branch that would build an unsealed carrier.**
`executor.rs:7155-7157` returns `open_virtual_file(state, b"0.00 0.00\n", …)` for `/proc/uptime`, but `synthetic_proc_content` handles `/proc/uptime` at `executor.rs:12890` and returns first, so the branch is unreachable. It is pre-existing, not introduced here, but it now silently contradicts the new invariant that all 17 fixed paths get a sealed carrier: were it ever reached it would hand the guest an unsealed, mode-0755 memfd. Required correction: delete the dead branch. Not blocking.

**5. Informational — the four headline v9 `LegacyLookup` corrections have no runtime oracle whatsoever.**
They are exercised only by unit tests that *inject* `RegularCreateDirectoryPolicy::LegacyLookup` into `state` (`executor.rs:29559-29560`, `29678-29679`, `31586`) and by the guest program's `if (expected_create_directory == ENOTDIR)` block (`tests/static_elf.rs`, patch lines 4798-4828) which **did not execute** on the `EarlyEinval` validation host. The unconditional native comparison in `synthetic_proc_direct_combined_open_matrix_preserves_policy_and_native_ordering` (`executor.rs:18958-18972`) is a real oracle for the mapping, but on this host it only ever exercises the `EINVAL` arm. The report discloses this honestly. I therefore checked the legacy claims against the pinned sources myself, and they hold:

- `linux/v6.3-fs-open.c:1156-1273` has no global `O_DIRECTORY|O_CREAT` rejection; `linux/v7.1-fs-open.c:1219-1225` does. Both call `build_open_flags` before `getname` (`v6.3:1332-1342`, `v7.1:1355-1364`), so placing the `EarlyEinval` check ahead of `read_c_string` at `executor.rs:7040` is correct, and the guest-test `EINVAL`-before-`EFAULT`/`EBADF`/`ENOENT` matrix (patch 4664-4681) is the right expectation.
- `linux/v6.3-fs-namei.c:3533-3544`: `O_EXCL` → `EEXIST` precedes `LOOKUP_DIRECTORY` → `ENOTDIR`, which precedes `may_open`'s `S_IFLNK` → `ELOOP` at `v6.3-fs-namei.c:3162-3164`. So `/proc/mounts|O_CREAT|O_DIRECTORY|O_NOFOLLOW` is `ENOTDIR` (not `ELOOP`), with `O_EXCL` it is `EEXIST`, and ordinary `/proc/mounts|O_NOFOLLOW` remains `ELOOP`. `synthetic_proc_create_directory_errno` (`executor.rs:212-227`) matches, and the v8 `ELOOP` it replaced was wrong.
- `linux/v6.3-fs-proc-fd.c:221-241` (`proc_lookupfd_common`) returns `ERR_PTR(-ENOENT)` directly for a missing, non-numeric, or leading-zero leaf; `v6.3-fs-namei.c:3393-3404` propagates it from `out_dput` **before** the `create_error` fallback at `3421-3424`, and `create_error` from `may_o_create` is never consulted because the dentry is negative only in the create branch. The earlier reviewer's proposed `EACCES` is refuted; `FdinfoPathTarget::MissingFinal` → `ENOENT` (`executor.rs:1984`, `7079-7080`) is correct.
- `v6.3-fs-namei.c:3466-3469` returns `-EISDIR` on the create side for a trailing slash, after the parent walk has already resolved `/proc/<pid>`, so gating `EISDIR` behind `fdinfo_task_generation` (`executor.rs:7063-7077`) is the correct order.

## Conclusions by area

**Sealed-carrier integrity — sound, and it closes a real base defect.** At base, `open_synthetic_proc` (`base/.../executor.rs:12828-12859`) inserted the `memfd_create` descriptor itself into the guest table, so the 17 fixed `/proc` snapshots were exposed `O_RDWR`, unsealed, and mode ~0755 — `write`, `ftruncate`, and `fchmod` on a "read-only" `/proc/uptime` fd would have gone through. (The base test at `base/.../executor.rs:17895` only checked that a *writable open* was refused, never `write` on the read-only-opened fd.) At head, `executor.rs:13124-13201` creates with `MFD_CLOEXEC|MFD_ALLOW_SEALING`, writes the content, `fchmod`s to `0o444`, adds `F_SEAL_WRITE|GROW|SHRINK|SEAL`, re-reads and requires exactly that mask or that mask plus `F_SEAL_EXEC`, then opens `/proc/self/fd/<construction>` `O_RDONLY` (or `O_PATH`) and `drop`s the construction handle at `13189` before `insert_file_with_flags` at `13191`. Every early return drops the construction `File`; `insert_file_with_flags` retires the file on `EMFILE` or identity-allocation failure. `F_SEAL_WRITE` cannot fail with `EBUSY` here because no shared writable mapping exists. I traced the write vectors: `write`/`writev` → `ensure_writable` → `EBADF` (`5264-5275`); `pwrite64` → the `proc_files` arm at `5759-5772`; `ftruncate` → `EINVAL` at `6791-6796`; `fchmod` → `EPERM` at `12332-12338`; `mmap MAP_SHARED|PROT_WRITE` → `EACCES` at `14369-14371`; guest proc-fd reopen → `EACCES`/`EINVAL` at `7499-7510`. The one path that reaches a host `O_RDWR` description is an SCM_RIGHTS round-trip (`received_proc_inode` returns `None` for a memfd, so the received fd loses its `proc_files` classification and the `regular_proc` gate no longer applies); under a root supervisor the mode-0444 check would not stop the reopen either — and this is exactly the case the seal exists for: the write then fails `EPERM` in the kernel. Defence in depth holds.

**Determinism — preserved, with one new host-dependent surface.** Content bytes are unchanged; the carrier is now immutable, which strictly increases determinism. `sanitize_proc_stat`/`synthetic_proc_statx` (`13301-13366`) still zero all timestamps and substitute the FNV-1a inode and synthetic dev, and the removal of the base `lseek(0)` is compensated by the fresh description starting at offset 0. The new nondeterminism surface is host-kernel dependence (finding 2). The SCM_RIGHTS declassification noted above also drops the guest back to the raw memfd inode — pre-existing, and covered by the disclosed SCM_RIGHTS-identity nonclaim.

**Linux semantics — materially improved and, where I could check against pinned source, correct.** Verified directly against `linux/`: the `O_PATH`-beats-everything reduction (`v7.1-fs-open.c:1170-1172`) is now modelled by `LEGACY_O_PATH_FLAGS` (`executor.rs:197-198`, `7167-7171`), which also fixes `uses_mode`/`named_create` for `O_PATH|O_CREAT`; `invalid_legacy_tmpfile_flags` (`201-210`) reproduces `v6.3-fs-open.c:1204-1209`'s `O_TMPFILE_MASK` test exactly, including the `ACC_MODE(3)` write-capable case; `ksys_pwrite64`'s `pos<0 → EINVAL` before `fdget`, then `EBADF`, then `FMODE_PWRITE → ESPIPE` (`v6.3-fs-read_write.c:686-704`) is reproduced at `executor.rs:5747-5772`, and `seq_open` clearing `FMODE_PWRITE` (`v6.3-fs-seq_file.c:76-85`) justifies `ESPIPE` for the 15 seq-file paths while `/proc/self/cmdline` and `/proc/sys/kernel/osrelease` correctly give `EBADF` via `vfs_write`'s `FMODE_WRITE` check. `synthetic_proc_every_regular_surface_matches_native_pwrite_result` (`18060-18115`) is a genuine oracle — it derives the expectation from the production classifier and then compares against a real host `pwrite` on each of the 17 paths, and `final-native-open-matrix.log:2-18` independently records the same 15×ESPIPE / 2×EBADF split. `ftruncate` on `O_PATH` correctly yields `EBADF` (kernel `fdget` masks `FMODE_PATH`) and `EINVAL` for a live non-writable regular description. The low-32-bit fd decoding now matches `unsigned int fd` for `pwrite64`, `ftruncate`, `fchmod`, and `mmap`.

**Lifecycle and locking — no regression found.** `FdinfoDescription::observe` (`1736-1803`) keeps the documented seq → one file table → lifecycle order and takes no new locks; `ensure_fdinfo_content_supported` (`2008-2025`) explicitly avoids locking `fdinfo_table`, which is safe because `open_file` holds exclusive `&mut state`. Every refusal in `open_fdinfo` precedes `open_synthetic_proc`, so no carrier, sequence state, or table entry is allocated on failure — pinned by `assert_fdinfo_rejection_does_not_allocate` (`29344-29400`), which snapshots `files`, `fd_entry_ids`, and `fdinfo_files` keys around each rejected open. The generation binding survives leader exit with a live worker (`31562-31680`), including with `LegacyLookup` injected after the leader dies, and dead-parent `ENOENT` correctly precedes the legacy create errors. `synthetic_proc_nofollow_fds` is propagated through `dup`/`dup2`/`dup3`/`F_DUPFD`, cleared on `close`, filtered on exec, copied on fork, and round-trips through `FileTableState` — all asserted at `19259-19350`. The carrier fd can never collide with an fdinfo `target_fd`, since `target_fd` must be live for the open to proceed.

## Residual and nonclaim audit

Accurately bounded, and none of them invalidates the narrower claims actually made:

- **Generic virtual-file carriers unsealed and writable through proc-fd** (`/proc/self/loginuid`, `/dev/urandom`, one cpufreq path). Confirmed real: `open_virtual_file` (`base` and head, `executor.rs:7046-7083`-equivalent) omits `MFD_ALLOW_SEALING` and leaves the default memfd mode, and the new test proves a successful `O_RDWR` reopen and 1-byte write. The claim is limited to exactly the three sampled paths; the report says so. Determinism is not broken — the mutation is a deterministic function of guest actions on a per-open carrier — and native `/proc/self/loginuid` is genuinely writable, so this is a fidelity gap of bounded consequence.
- **Fdinfo `O_PATH` (including `O_PATH|O_NOFOLLOW`) remains `ENOSYS`; bare fdinfo `O_CREAT`, `O_CREAT|O_EXCL`, `O_TRUNC`, `O_DIRECT` ordering mismatched.** Confirmed at `executor.rs:2050-2060`. Accurately stated.
- **Exact `/proc/self/fdinfo/` ordinary open / `O_DIRECTORY` / `O_TMPFILE` remains `ENOENT`.** Confirmed: base already returned `ENOENT` for the empty suffix, and `FdinfoPathTarget::EmptyFinal` preserves it at `7076`. Only the legacy create-directory arm changes. Accurately scoped. I also found an *undisclosed* sibling of the same class: `/proc/self/fdinfo/<n>/` (trailing slash after a numeric leaf) parses as `MissingFinal` → `ENOENT` where Linux gives `ENOTDIR` (`executor.rs:1975-1985`). Pre-existing, identical in base, immaterial.
- **Proc-fd `O_PATH|O_NOFOLLOW` fail-closed as `ELOOP`.** Confirmed at `7472-7474` and `7485-7491`, and the test at `19693-19707` asserts the native result is success while the guest deliberately refuses. Honestly labelled as fail-closed, not as parity.
- **Direct `/proc/mounts` `O_PATH|O_NOFOLLOW` link identity.** Confirmed divergent: `open_file:7102` skips the `ELOOP` arm for `O_PATH`, so the guest gets an `O_PATH` handle to the memfd and `fstat` reports `S_IFREG 0444` where Linux reports the symlink. Disclosed.
- **Fdinfo statx truncated mask.** Confirmed exactly: `synthetic_proc_statx:13342-13349` yields `0x71f`, omitting `STATX_ATIME|MTIME|CTIME` from the requested `0x7ff`. `executor.rs:29512-29522` asserts the native side reports the full mask and the guest does not — the mismatch is pinned as a mismatch, not as parity.
- **Credential-exact root mutation parity not claimed.** Confirmed and substantiated: root can `chmod` a procfs PDE via `proc_notify_change`, so the guest's unconditional `EPERM` at `12332-12338` genuinely diverges under a root supervisor. The real-KVM guest proves `getuid()==geteuid()==0` immediately before requiring `EPERM` (patch 4692-4695), so the divergence is explicit rather than hidden.
- **Future implicit seal → `EOPNOTSUPP`.** Confirmed at `13165-13167` and pinned by `synthetic_proc_seal_policy_accepts_only_supported_kernel_shapes` using a reserved `0x40` bit.
- **No 5.8–6.3 runtime.** Confirmed: `installed-modules.txt` and `kernel.txt` show only 6.13.2 / 6.19.2 / 7.1.3, and no artifact claims otherwise. See finding 5.
- **mmap type / `MAP_SHARED_VALIDATE` / later `mprotect(PROT_WRITE)` provenance.** Confirmed out of scope and confirmed harmless to the safety claim: the backend copies file-backed mappings into guest memory (`executor.rs:14376+`), so even a wrongly-permitted writable mapping cannot mutate the carrier.
- **Prerequisite only — no syncfs, no SCM_RIGHTS carrier identity, no identity marker, no record/replay, no full parity.** Confirmed by inspection of the whole diff: nothing in the 4,137/209 change adds any of these.

One residual is *not* disclosed and should be: finding 2 (host-kernel-dependent errno).
