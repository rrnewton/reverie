KVM needs a separate guest fdinfo implementation in Reverie. The existing Hermit resource guard cannot fix this open failure: it selects the inode while normalizing bytes after a successful fdinfo open/read, and the backend refuses the open before that code runs. Removing the backend's real-procfs refusal would expose supervisor descriptor state and would not implement guest semantics.

The observed call is guest syscall93, openat(AT_FDCWD, "/proc/self/fdinfo/0", O_RDONLY|O_CLOEXEC), returning EACCES. At that point guest fd0 is an ordinary reopened file and guest fd5 is its duplicate; both already passed exact descriptor stat checks. Native Linux and the candidate ptrace run permit this same-process lookup. The fdinfo inode must identify the object named by guest fd0 and agree with its fstat result. Its position and file-status flags describe that open file description, while close-on-exec remains a descriptor flag. A closed/missing guest descriptor has no fdinfo entry and must not fall back to a supervisor descriptor with the same number.
