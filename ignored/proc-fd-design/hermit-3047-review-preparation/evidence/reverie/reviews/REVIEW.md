The design needs the three refinements below before implementation. Its core direction is sound: ordinary descriptors should retain their real object identity, fdinfo must resolve the original task at the Linux observation point, and mountinfo must describe the namespace in which the backend actually opens files. This is a design review, not approval of unimplemented source or evidence of passing native or guest tests.

1. Bind the task selected by the pathname. Do not always save the opening thread's TID. /proc/self/fdinfo and /proc/<TGID>/fdinfo name the leader; /proc/thread-self/fdinfo names the calling thread. Their tables normally coincide, but their lifetimes differ when the leader exits while a worker remains. The current guest_fd_path at executor.rs:5107–5119 treats the spellings alike for immediate metadata; a persistent fdinfo target cannot inherit that simplification. Save the appropriate original task generation, preserve it across descriptor inheritance, and check that exact membership at each record generation. Include the leader-exit/live-worker distinction in a focused control or keep an unsupported spelling explicitly unavailable.

The lifecycle addendum is correct: replace_after_exec mutates the existing file-table Arc in place (executor.rs:2336–2356), fork creates a distinct Arc (1768–1769), a thread shares it (1876), and release_files_on_exit replaces only the exiting executor's reference (2054–2061). reset_after_exec preserves a live task generation (elf.rs:322–333). Retirement precedes file release and consuming exit hooks (runtime.rs:1487–1497). A weak table reference plus existing generation/liveness checks therefore suffices for the supported targets; a new registry is unnecessary. A live sibling retaining the table must not keep the dead target readable. Both direct and Tool runners create ElfExecutor (vm.rs:2775–2786; runtime.rs:1871), so this representation can serve both paths.

2. Snapshot status flags together with the descriptor's guest CLOEXEC. Linux fd.c:39–49 samples f_flags and close_on_exec while holding the target table lock, then pins the file. In this backend, File::try_clone/F_DUPFD_CLOEXEC creates supervisor descriptors with CLOEXEC independently of guest cloexec_fds (executor.rs:5637–5655); F_SETFD and F_SETFL are serialized through the guest table (10692–10731,3065–3077). At generation, sample F_GETFL and guest CLOEXEC under that same table lock. Replace the native fdinfo flags line with that pair after reading the pinned file. Merely clearing supervisor CLOEXEC afterward is insufficient if the status flags and guest descriptor bit were sampled on opposite sides of another update. The worker has acknowledged this requirement.

3. Preserve seq read position separately from the shared file offset. Linux seq_read copies the caller's position into/out of ki_pos (seq_file.c:161–164); pread can change the shared seq buffer/read_pos without changing file.f_pos. A subsequent read or SEEK_CUR can therefore require traversal. A changed nonzero seek may generate the record and return ENOENT immediately; on that failure seq_lseek resets both positions and the retained record (308–339). One cursor plus a byte buffer is insufficient unless it separately represents these states. Required controls include pread followed by ordinary read, changed-nonzero seek failure/reset, and inaccessible/partially accessible read buffers with exact returned count and cursor effects. Keep zero-count behavior and unsupported vector operations explicit. The worker's current nine-case native fixture already covers repeated pread0/SEEK_CUR0 and successful nonzero seek, but the two additional sequences are follow-ups, not claimed coverage of that frozen attempt.

Lock and progress constraints: execute releases the reader's table lock before nonmutating read/pread/lseek (executor.rs:3065–3077). Keep that release. Open/dup/close hold their own table lock; they must not generate fdinfo text or acquire a description's sequence lock while propagating its Arc. Record generation may serialize on its own description, briefly check lifecycle/table state and clone a file, then release lifecycle/table locks before host I/O. Never acquire a second reader table, retain a table lock through a callback/await, or recursively resolve an unsupported fdinfo/synthetic target. The final source must show one consistent lifecycle/table order and no inverse acquisition. These are synchronous syscall observations, not a reason to add background completions, a new clock, or scheduler ordering rules. Hermit's full-quiescence scheduler waits for runnable threads' next requests (scheduler.rs:4026 onward); waiting for another guest while retaining a file-table lock could prevent that progress.

The mount addendum is also correct. Hermit's existing MountIdPool first requires valid initialization, then assigns a deterministic ID to a genuine newly observed nonzero mount ID and records it in unlisted_order (tool_global.rs:329–359). That field is provenance, not a whitelist. A real pipefs ID absent from visible mountinfo needs no guessed zero/root identity, added exemption, or pool change. Preserve completed-namespace IdentityGuard resolution and capture (container.rs:302–318; run.rs:4901–4912), and compare the backend snapshot with that same namespace before Tool initialization. Remove only the obsolete synthetic 0:1 mapping/cleared provenance at lib.rs:1956–1986. Public-library callers must capture the real backend namespace rather than use virtual guest PID as a host /proc PID. Fork/exec must retain the established snapshot; namespace changes remain outside this design. Raw paths still pass the existing shared sanitizer. If mounts spellings remain synthetic, report that surface as unresolved.

Separate existing Hermit limitation: a backend-correct fdinfo does not establish dynamic fdinfo correctness through Detcore. files.rs:1244–1267 derives the normalized inode/flags from the reader's current target_fd entry after obtaining backend bytes. After fork, an inherited fdinfo must still observe its original parent target, but this lookup can substitute the child's replacement object. ProcfsFile keeps only target_fd and cached contents (procfs.rs:377–384); needs_snapshot tests for absent contents (843–844), and rewind only invalidates timer-slack, not fdinfo (1109–1114). Thus backend fork/rewind controls and the current unchanged descriptor-reuse guest are distinct from a complete Hermit fdinfo claim. Record these existing limitations as follow-up work; do not expand or weaken the current fixture to conceal them.
