## Findings

**F1 — MINOR (test defect, concrete). `hermit-cli/tests/cli.rs:3465-3483`: the two Hermit legs of the new descriptor-reuse control run with the harness's working directory, while the native leg is deliberately given one.**
`native` gets `.current_dir(native_dir.path())` (line 3458). The `ptrace`/`kvm` legs get no `current_dir` and no `--workdir`. The fixture calls `mkstemp("stdio-inode-a-XXXXXX")`/`"stdio-inode-b-XXXXXX"` relative to the guest cwd and only `unlink`s them on the success path (`tests/c/fixtures/stdio_inode_identity.c`, `check_reuse` head and its final `CHECK(unlink(path_a) == 0 && unlink(path_b) == 0)`). Reachable behavior: under a plain `cargo test`, the guest creates two files inside the repository checkout; on any `CHECK` failure between `mkstemp` and the final `unlink` the two files are left behind in the tree; on a read-only checkout the control fails for a reason unrelated to descriptor identity. In the official lane this is masked, because `append_hermit_args` injects `--mount=type=tmpfs,target=/test --workdir=/test` when `HERMIT_E2E_EMPTY_WORKDIR` is set, so I do not treat it as CI-visible. Smallest correction: add `.current_dir(native_dir.path())` to the two backend commands — that path is under `CARGO_TARGET_TMPDIR`, i.e. not under `/tmp`, so KVM's documented `CONTAINER_REPLACED_TMP` cwd refusal (`hermit-cli/src/lib.rs:1923-1944`) is not triggered.

**F2 — Residual, pre-existing, not introduced. `detcore/src/tool_local.rs:718` with `stdio_resource` at `843-850`: live discovery still labels *any* descriptor first seen at slot 0/1/2 as `ContainerStdin/Stdout/Stderr`.**
Because the new guard keys on the resource, a SaBRe-backend descriptor that Detcore never observed being created and is first resolved at slot 0-2 (`discover_live_file_metadata = backend == Backend::Sabre`, `hermit-cli/src/lib.rs:2338`) acquires an inherited-stream resource and therefore the fixed inode, defeating the repair on that backend. This is not a regression: base applied the fixed inode by fd *number* unconditionally, so SaBRe was strictly worse before. The new fixture is run on native/ptrace/KVM only, so the repair is simply unproven for SaBRe. If tightened later, the narrow fix is to restrict `stdio_resource` labelling to the initial `ThreadState::new` discovery (`tool_local.rs:2143-2150`) and exec restoration rather than the generic `with_detfd` fallback.

**F3 — Retained Linux-semantics deviation, explicitly scoped out, not worsened.** For genuinely inherited streams the fixed inode remains keyed to the *numeric slot* and is applied on the `fstat` entrypoint only:
- `handle_stat_family` overrides `StatFamily::Fstat` only (`detcore/src/syscalls/files.rs:2669-2676`); `handle_statx` passes `None` (`files.rs:2702`). So `fstat(1)` on inherited stdout reports 1001 while `newfstatat(1,"",AT_EMPTY_PATH)`, `statx(1,"",AT_EMPTY_PATH)` and `stat("/proc/self/fd/1")` report the pooled inode. Linux reports one `st_ino` for all of these.
- `dup2(1,0)` yields `fstat(0)=1000` and `fstat(1)=1001` for a single open file description — asserted as intended at `detcore/src/tool_local.rs:1136-1143` (*"inherited streams retain the existing numeric-slot outcome"*).
Both hold identically in base, and the fixture deliberately routes inherited descriptors through `SYS_fstat` (`stat_fd`, with the comment *"Keep inherited-stream bookkeeping on its original fstat entrypoint"*). This is disclosed scope, not concealment — but it means the PR's stat-route-consistency claim is true for **ordinary objects only**.

**F4 — Pre-existing soundness hole adjacent to the changed code, worth recording. `detcore/src/tool_global.rs:165` vs `detcore/src/consts.rs:21,25`.**
`InodePool::new()` sets `next_inode: 1` and mints monotonically, while the fixed stdio identities are `DET_SPECIAL_INODE_OFFSET + fd` = 1000/1001/1002. `DET_INODE_OFFSET = 9000` — the constant whose doc comment says it is *"the starting point for deterministic inodes other than those addressed by DET_SPECIAL_INODE_OFFSET"* — is **dead**: a repository-wide grep finds no consumer. A run that determinizes ≥1000 distinct raw inodes therefore mints 1000-1002 from the pool and collides with the inherited-stdio identities, so two distinct objects report the same deterministic `st_ino` in one run. That is ~1000 distinct files, easily reached by a real program. Base is identical, and this change only marginally increases pool traffic (ordinary fd 0-2 objects now take pooled inodes). Smallest correction, if taken up separately: seed the pool at `DET_INODE_OFFSET` or reserve `1000..=1002`. **Not a reason to hold this PR.**

**No defect found in the descriptor repair itself.** The guard is `fd ∈ 0..=2 AND resource ∈ {ContainerStdin,ContainerStdout,ContainerStderr}` (`detcore/src/syscalls.rs:48-58`), so the set of `(fd, object)` pairs receiving a fixed inode is a **strict subset** of base's `fd ∈ 0..=2`. I checked every consumer and there is no path where the new code assigns a fixed inode that base did not:

|---|---|---|
| `fstat` | `files.rs:2669-2676` | override only for inherited; lookup after `inject`, `.ok().flatten()` so an unregistered fd (EBADF) falls to the ordinary pool without altering the kernel's own errno |
| fdinfo `ino:` | `files.rs:1248-1268` | keyed on the **target** fd's resource, not the reader's |

`deterministic_stdio_inode` now has exactly one remaining reachable caller, the raw matcher at `namespace.rs:192-203`, whose input array is itself guarded. Coverage of the six consumers is complete.

Cross-check on the fixture's own arithmetic: `"stdio-inode-descriptor-reuse-ok\n"` is exactly 32 bytes, matching the recorded 32-byte success stdout for both runtime legs. The ordinary-object routes are mutually consistent by construction — `fstat`, `newfstatat`/`statx` with `AT_EMPTY_PATH`, path stat, fdinfo `ino:` and pipe `readlink` all reach `determinize_inode(raw)` through the same pool for the same raw inode.

**Mount provenance (`hermit-cli/src/lib.rs:1954-1979`, call site `:1990`) is correct and fails closed.** Order of operations: refuse uncaptured-but-nonempty vectors *before* calling `capture`; propagate capture errors with context; compare exactly (`!=`, not ordered-subset) when provenance was supplied; adopt the ambient order only when none was supplied. `config` is mutated only after every refusal point — the four new tests assert byte-identical `serde_json` snapshots across all six mismatch vectors plus malformed/duplicate/unknown-optional-field inputs and a `PermissionDenied` capture. Root rewrites and `fdinfo_unlisted_mount_ids` are preserved verbatim; only `mountinfo_device_rewrites` is cleared, and nothing fabricates a `mnt_id` or a device. The synthetic `0:1` rewrite and the `mountinfo_root_rewrites.clear()`/`mountinfo_mount_ids.clear()` block are deleted because the backend now serves the real namespace (`reverie-kvm/src/proc_mounts.rs`, installed at `elf.rs:1033`), not to make a comparison pass. Two consequences I verified rather than assumed:
- Both the `IdentityGuard` capture (`container.rs:314-319`, called from `run.rs:4906-4910` inside `with_container`) and `prepare_kvm_mountinfo_config`'s recapture read `/proc/self/mountinfo` in the same process inside the completed container, and the backend snapshots the same namespace at ELF install. The T1→T2 window between the CLI recapture and the backend snapshot is real but bounded and **fails closed**: a row appearing later is rejected downstream by `mount_ids_are_ordered_subset` (`detcore-model/src/procfs.rs:29-38`, via `MountIdPool::validate_mountinfo_order`, `tool_global.rs:310-327`), producing a refusal, not a fabricated identity.

Determinism caveat, not a defect: for `--no-namespace`/library KVM callers the guest now sees the *host's* real mountinfo text instead of one synthetic row. Identities are determinized through the shared pools, but pathnames and row content are host-dependent. This is exactly the pre-existing ptrace behaviour, so it is parity rather than a new leak.
