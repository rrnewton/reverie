## Finding 4 — confirmed by running, not by reading

The refusal says the model-backed `F_GETFL` loses `O_LARGEFILE`, so a raw `0x8001`
becomes `0x1`. Both mechanisms are present:
`OFlag::from_bits_truncate(status_flags)` at `detcore/src/tool_local.rs:663` and `:741`,
and `detcore/src/syscalls/files.rs` `F_GETFL` returning `detfd.status_flags()` from the
model for contained stdio instead of asking the kernel.

I built a small program against the pinned `nix` 0.30.1 and `libc` 0.2.189 and ran it:

```
libc::O_LARGEFILE            = 0x0
OFlag::O_LARGEFILE.bits()    = 0x0
from_bits_truncate(0x8001) -> 0x0001   LOST BITS
from_bits_truncate(0x8401) -> 0x0401   LOST BITS
from_bits_truncate(0x0001) -> 0x0001   preserved
from_bits_truncate(0x8000) -> 0x0000   LOST BITS
```

`nix-0.30.1/src/fcntl.rs:169` declares `O_LARGEFILE` in `OFlag`;
`libc-0.2.189/src/unix/linux_like/linux/gnu/b64/mod.rs:194` defines it as `0`. So the
flag set cannot represent bit `0x8000` at all, and the newly authoritative `F_GETFL`
returns the truncated value.

**This bears on the change's own evidence.** An earlier comment reports
`containment probe, ptrace 0x8001 -> 0x8001 contained` and the same for KVM. The model
cannot hold `0x8000`, so whatever that probe reads, it is not the model-backed
`F_GETFL` for a contained descriptor. Either the probe measures a different path or the
descriptor was not contained at the time. Worth resolving, because that probe is cited
as the containment evidence.
