Findings

1. P1 — Ordinary redirected KVM write/writev now reaches an unimplemented Pwritev2 dispatch arm.

At detcore/src/syscalls/files.rs:2018–2115, record_or_replay_inherited_write translates an ordinary Write or Writev on logically append-mode inherited regular output into Pwritev2(offset=-1, RWF_APPEND). The containment policy intentionally leaves the host OFD's O_APPEND bit clear. The conversion is reached by handle_write and handle_writev after their existing resource admission; it is not restricted to guests explicitly requesting a positioned syscall.

The complete real path is hermit-cli/src/lib.rs:1944–2130 (run_kvm, including run_static_elf_with_tool::<Detcore> at 2093), Detcore::init_thread_state, ThreadState::new/setup_stdio's host fstat, the changed write handlers, then the Tool guest's nested injection. Cargo.lock pins Reverie to 8c8c0a57649c9ffbf8a7a14291a64320f64b935f. In that exact source, reverie-kvm/src/runtime.rs:495–498 calls executor.execute; executor.rs:2070–2140 dispatches to execute_basic_syscall_with_output. Its match at 299–320 implements Write, Writev and Pwrite64, but has no Pwritev2 arm anywhere in the executor. The fallback at 830 returns ENOSYS. The original Write path at 2296–2350 does support ordinary host stdout output.

Concrete trigger: provide stdout as a regular file at an offset before EOF, let the guest successfully set O_APPEND, then call ordinary write(1, ...). The new implementation returns ENOSYS through the pinned executor instead of appending. This is a regression of ordinary write, not merely the pre-existing absence of a guest Pwritev2 syscall. Captured synthetic-FIFO output is a different path and does not disprove this regular-host-output trigger. The new run_kvm_guest_cannot_mutate_hermits_stdout_flags test preserves the right prefix/output/status oracle, but the actual portable campaign filtered KVM tests; it never qualified this case.

Required change: integrate an actual supported append implementation into the executor used by this PR, or another coherent backend implementation of the same contract. The disclosed dependency on https://github.com/rrnewton/reverie/pull/538 is not present at the pinned executor and does not fix this head. Preserve host and captured-output distinctions, the original ordinary-write assertion, error and offset semantics, and containment. Do not forward the guest's full physical status word or exclude KVM. After repair, the existing ordinary-write KVM control plus relevant host/capture cases are the focused runtime evidence needed; no universal full-profile gate is proposed.

2. P1 — SaBRe bypasses inherited-OFD alias discovery, so contained flags split one Linux description into independent models.

hermit-cli/src/lib.rs:2327 sets discover_live_file_metadata for Backend::Sabre. ThreadState::new at detcore/src/tool_local.rs:2328–2340 takes a different branch for that configuration: it calls discover_fd_from_current_process separately for fd 0, 1 and 2 and returns no alias error. It never calls the new setup_stdio_with/kcmp path. discover_fd_from_current_process at 720–756 calls add_fd, whose 780–792 implementation allocates a new OpenFileId and DetFd/Arc for each descriptor. A later with_detfd does not rediscover an existing descriptor. The actual pinned experimental/reverie-sabre/src/reverie_adapter.rs:419–425 constructs Detcore from this config and calls init_thread_state(tid, None) for a fresh root.

Concrete trigger: inherited stdout and stderr are dup aliases, as with 2>&1. Guest F_SETFL(stdout, O_APPEND) changes only stdout's logical description. The new F_GETFL(stderr) reads its separate cached description and omits O_APPEND; a subsequent ordinary stderr write does not take the append conversion and can overwrite the file at its current offset. Before this change the physical shared OFD supplied these flags. Sharing Arc values on the normal setup_stdio path does not repair the branch SaBRe actually uses.

Required change: preserve inherited description equivalence in the SaBRe initialization/discovery route too, while retaining its live descriptor type and nonblocking behavior and the new fail-closed alias-error semantics. A control must exercise the real discover_live_file_metadata configuration with duplicated descriptors and independent opens of the same inode; testing only setup_stdio_with is insufficient. No SaBRe execution was performed in this review.

3. P1 — DBT's contained status state has the wrong lifetime across real fork and exec.

The new logical status resides in OpenFileDescription behind a process-local Arc<Mutex<...>> (detcore/src/fd.rs:207–230, set_logical_status_flags at 654). FileMetadata::fork_for shares that Arc among modeled processes within a single address space; FileMetadata::for_exec retains descriptions in the ordinary hosted Tool path. Those mechanisms do not cover DBT's actual copied or replaced address spaces.

For normal DBT fork, detcore-dbt/src/lib.rs:1336–1395 explicitly takes the copied DynamoRIO process's copy-on-write parent allocation and initializes the child's state from it. The pinned native client has actual normal-fork lifecycle handling; the refusals for unsupported CLONE_FILES/CLONE_VM combinations do not refuse ordinary fork. reverie_dbt_runtime_process_clone_result at 1593–1623 explicitly acknowledges independently mutable copied state and invalidates flock knowledge, but does not move status flags into a shared authority or synchronize them. After a child successfully sets contained O_APPEND, the parent's model is unchanged. Following wait or another deterministic synchronization, the parent reports stale F_GETFL and can write without append. A process-local Arc is not cross-process OFD storage. Forwarded O_NONBLOCK can similarly leave another copied model stale.

For exec, the native lifecycle branch at detcore-dbt/src/lib.rs:2175–2210 calls send_dbt_prepare_exec (474–505) and then delegates the actual exec. That message carries identity/mm and an empty BTreeSet, not logical inherited-OFD status. The new native image initializes fresh per-thread scratch (pinned client.c:3943) and a fresh root Tool state; setup_stdio can recover only the unchanged physical flags. Guest-set logical O_APPEND disappears across successful exec even for an inherited descriptor without FD_CLOEXEC. The normal in-process for_exec helper is not the path that preserves this state in DBT.

These are new consequences of replacing the kernel OFD's flag authority with a local model; the pre-existing copied runtime by itself is not a sufficient explanation for accepting them. Required change: give logical inherited-OFD state an authority/lifetime shared by actual fork descendants and carry it through successful exec reconnect, preserving descriptor aliases and close-on-exec behavior. Add focused child-set/parent-observe-and-write and set-then-exec controls through the real DBT paths. Preserve physical containment, successful ordinary fork/exec semantics and scheduler ordering. No DBT guest run was performed to infer this finding. The author confirmed no existing repair or status handoff path was known; the source trace is the basis for the finding.

4. P2 — Model-backed F_GETFL can lose an immutable raw status bit during initialization.

setup_stdio_with at detcore/src/tool_local.rs:666 and the live discovery branch at 742 construct OFlag with from_bits_truncate(status_flags). The newly authoritative F_GETFL at detcore/src/syscalls/files.rs:2868–2880 then returns the stored bits instead of the kernel word. In the retained nix 0.30.1 source, OFlag enumerates libc constants; GNU 64-bit libc 0.2.189 defines O_LARGEFILE as zero (gnu/b64/mod.rs:194), whereas the Linux UAPI raw O_LARGEFILE is octal 00100000 (0x8000). Thus a raw inherited regular-file word such as the implementation's own retained historical 0x8001 example becomes 0x1 in this model. The access mode survives, but exact F_GETFL observability does not. This narrower issue is independent of the three blockers and was not newly run.

Preserve the complete raw initial status word, excluding only descriptor-local flags that really are separate, and apply the five-bit F_SETFL mask when modifying it. Include a full-word initialization assertion using a raw bit not represented by the platform OFlag constants. Source copies and provenance limits are in raw-status-word-source-binding.json: package versions match Cargo.lock, but this retained Cargo source directory has no per-file .cargo-checksum.json, so I do not claim a fresh package-integrity verification for these copies. The installed Linux header is a reference, not a guest build observation.
