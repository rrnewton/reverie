Instrumentation and phase order

PrepareProbe contains three optional one-shot callbacks: BeforeWithdraw, AfterWithdraw, BeforeAcknowledge. RunEntry::cleanup invokes them outside the gate mutex, passing the exact participant ID and run generation. CountedVcpu has already returned from its actual KVM_RUN and completed its real clock interval before invoking normal entry finish. BeforeWithdraw therefore observes the still-published Running target after ioctl/clock cleanup; AfterWithdraw observes Retiring before final drain; BeforeAcknowledge observes actual drain and saved-mask restoration while retirement is still counted. Hooks are observational and are taken out of their own mutex before invocation. No Mask or Entry guard moves to another thread or crosses a driver async suspension. Polling the separate close future once inside a synchronous observer is not an await of the driver.

The three race declarations are:

- late_kick_after_successful_exit_is_drained_before_acknowledgement: BeforeWithdraw checks that pending signal 64 is empty, then invokes the actual gate close with a sender that performs three real pthread_kill calls to the exact published pthread. The empty observation is explicit test activity; production still has one mandatory final drain. AfterWithdraw requires pending signal 64. BeforeAcknowledge requires no pending signal and exact restoration of every defined mask bit (1 through 64), including unchanged SIGURG/SIGUSR2. Close.finish must remain Pending at both intervening phases and become Ready only after actual acknowledgement wakes its registered waker.
- withdrawn_real_entry_has_no_sender_until_final_cleanup_acknowledges: close begins at AfterWithdraw while admission is otherwise Open. Its sender callback must never be invoked. The actual Retiring generation still prevents close completion through drain and restoration. This is a new close against a real withdrawn RunEntry, not a second close rejected merely because admission was already Closing.
- real_withdrawal_waits_for_serialized_sender_and_drains_its_kick: BeforeWithdraw starts a real closer thread. Its test sender pauses while holding the production gate mutex. The original thread then reaches Entry::withdraw. An explicitly armed cfg(test) acquisition observer tries that same real mutex; only an actual WouldBlock reports contention and releases the sender. It then performs the normal blocking acquisition. A successful try_lock does not report contention; poisoning remains a failure. The sender performs three actual pthread_kill calls before releasing the mutex; AfterWithdraw receives its real Closing value and requires one contention witness and all three sends. The original thread never reads registry state while depending on the sender to release that mutex. Sender waits are finite, and an owning rescue joins the sender on early assertion unwind.

The special acquisition observation is present only for the armed cfg(test) case. Unarmed tests use the original blocking lock statement; cfg(not(test)) retains the original statement. The observation proves that withdrawal's mutex acquisition was actually refused by the serialized sender, rather than inferring contention from a missing event or a delay. It does not assert that the OS scheduled a particular futex wait.

This tests actual reused generations and actual host-thread transfer, not merely construction of another signal mask guard.

Fault composition

mask_operation_errors_poison_after_safe_real_cleanup_and_preserve_causes exercises five operation selections for both mask states and both clock modes: install only, drain only, restore only, drain+restore, and install+drain+restore. The fault guard is thread-local, not Send, restores its previous TLS value, and permits one consumption per configured operation. The reported errors are exact retained Arc<Error::EntryControl> identities with distinct operation strings and errno values EACCES/EIO/EPERM.

The install seam reports the injected error before the actual mask ioctl; the enclosing real Participant::prepare/Entry::activate/RunEntry cleanup path must fail, withdraw, restore the real host mask, poison and acknowledge. No guest instruction or KVM_RUN may occur. This is an injected operation error, not a claim that the kernel produced EACCES.

Drain and restore seams remove their own one-shot before recursively performing the unchanged real operation. After that real operation completes, they report the injected error, retaining any additional real error as cleanup. Thus tests exercise Mask::finish's actual error composition and RunEntry acknowledgement without deliberately leaving a queued signal or unsafe mask behind. These are injected reported errors after real cleanup, not claims that sigtimedwait or pthread_sigmask returned the chosen errno. The fault-only producer queues three real signals while blocked to prove actual drain still occurs; sender authorization/order is qualified separately by the three race tests.

Every configured injected error identity must occur exactly once in both the returned error and retained gate error tree. Primary cause order must be install, otherwise drain, otherwise restore, with exact original errno. The registered gate waiter must wake. Before acknowledgement, state must still be Retiring and the actual mask restored with zero pending/delivered reserved signals. After acknowledgement it must be Stopped but poisoned: subsequent entry, copy, registration, ordinary admission and close all refuse. The second attempted run must not increment mask/RUN/clock counters. The retained backing sentinel, read only after the failed entry returned, distinguishes no guest execution for install refusal from one completed guest execution before drain/restore refusal. Guard consumption counts are exact; backend Drop removes its member. A separate real CountedVcpu then executes successfully on that same host thread, establishing that failure propagation did not strand a mask or queued signal.
