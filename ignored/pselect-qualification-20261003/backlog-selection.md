Why pselect6 is the next concrete increment:

- The unchanged guest uses zero timeouts, no signal mask, one owned pipe, ready/readable/writable/drained/EOF states, and requires all eight checks with a nonzero exit on failure: https://github.com/rrnewton/hermit/blob/5d8cf0cf1d9a087503bfe8b1df368df72b9c44d7/tests/c/poll_readiness.c#L65 and https://github.com/rrnewton/hermit/blob/5d8cf0cf1d9a087503bfe8b1df368df72b9c44d7/tests/c/poll_readiness.c#L115 . Its source blob is 65f60f33aa298f5a2d2f0879aedf51fe7f2b9a4e.
- There is actual consumer failure evidence, not only a stale manifest reason: https://github.com/rrnewton/reverie/issues/891#issuecomment-5966474857 . The glibc select wrapper invoked pselect6(4, ..., zero_timeout, NULL) and got ENOSYS. The fixture and manifest still select the same behavior on current Hermit main.
- Current producer dispatch is https://github.com/rrnewton/reverie/blob/47f0d8f7d74f1b46272866ef27241ed3234a21f6/reverie-kvm/src/executor.rs#L637 . Its pselect6_validation_preflight at line10198 validates memory/arguments, then unconditionally returns ENOSYS at line10259. The existing select helper starts at line10264; it is a reference for readiness construction, not a correct drop-in pselect6 implementation (timeval versus timespec, error/copyout order and raw fd-width rules differ).
- Consumer reach is concrete: https://github.com/rrnewton/hermit/blob/5d8cf0cf1d9a087503bfe8b1df368df72b9c44d7/detcore/src/syscalls/io.rs#L525 injects a zero-timeout pselect6 directly. A producer implementation can therefore reach this cell without changing the scheduler's blocking policy. The broader ppoll ownership problem remains at https://github.com/rrnewton/reverie/blob/47f0d8f7d74f1b46272866ef27241ed3234a21f6/reverie-kvm/src/runtime.rs#L242 .
- No open Reverie PR in the current five-PR list carries this implementation. https://github.com/rrnewton/reverie/pull/606 supplied only validation; https://github.com/rrnewton/reverie/pull/536 is closed without landing. Preserve issue620 as the full contract.
