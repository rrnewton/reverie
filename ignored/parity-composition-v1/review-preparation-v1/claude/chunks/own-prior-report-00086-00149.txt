### §13.5 — reverse group status: **refuted as a hazard, on source I read myself**

The author's argument is supplied as an argument. I tested it rather than accepting it, and I reach the same conclusion by a route that is immune to the omitted-caller objection.

`TaskLifecycleTable::exit` (`elf.rs:252-275`) is the whole answer:

```rust
let Some(task) = self.tasks.get(&tid).copied() else { return status; };
if task.generation != generation { return status; }
let exit = self.process_exits.entry((task.tgid, task.process_generation)).or_default();
if group { exit.group.get_or_insert(status); }
exit.last_thread = Some(status);
let status = exit.group.unwrap_or(status);
```

For a live current-generation task this is **first-group-status-wins, and the return is the group value**. `ElfExecutor::take_exit` (`executor.rs:4234-4246`) holds the shared `signal_transaction` mutex, locks `task_lifecycle`, and **returns that table value**, not the raw staged status. CLONE_THREAD workers share the table (`task_lifecycle: self.task_lifecycle.clone()`, `elf.rs:840`) and the same key: `state.pid = self.state.pid` (`executor.rs:2372`) and `register` reuses an existing same-`tgid` task's `process_generation` (`elf.rs:167-174`). `GuestThreadGroup::request_exit_group` (`vm.rs:448-452`) is a second `get_or_insert` — first published value wins.

So there are two independent first-wins collapses in series, and the arm's `exit.status` at `runtime.rs:3250` is already the collapsed value before it is either published or returned. **Because the guarantee lives in `exit()`'s own semantics, no unread caller can produce a second raw status for a live current-generation task.**

One thing the author does not say, which I will, because it resolves my V6 N1 sub-question rather than merely deflecting it: the arm's failure to consult `guest_thread_group_exit_status()` — the asymmetry with `cancelled_tool_thread_status` (`runtime.rs:2155-2168`) that I flagged — is not an omission but the **better** of the two routes. `cancelled_tool_thread_status` is entered when the thread has no exit of its own and must obtain a status from somewhere, so it reads the group cell. The timestamp arm is entered only when the thread *has* staged its own exit, so `take_exit` is available — and the group cell is published *after* the lifecycle commit, so it can lag. The arm reads the earlier and authoritative source.

**Residual, which I state and do not claim proved either way:** the missing/mismatched-generation branch returns the raw status. I found no timestamp path that removes its own generation and then reaches `take_exit` again, and the arm takes the pending exit exactly once. Decisively for this verdict, that branch is **shared by every caller of `take_exit`**, including `finish_static_elf_thread` (`vm.rs:3358`, `:3366`) and `retire_current_thread` on every ordinary exit. A defect there is pre-existing backend behaviour that this PR inherits, not one it introduces. The reverse publication interval remains unmeasured; mode 10 pins worker-first only.
