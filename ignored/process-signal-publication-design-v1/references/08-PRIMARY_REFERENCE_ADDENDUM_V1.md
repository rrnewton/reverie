# Primary-reference correction to the frozen KVM alarm proposal

The reference gap is resolved, but the references **do not approve the frozen delivery design**. They confirm process-directed SIGALRM, standard-signal coalescing, blocked/ignored no-interruption, pending-state lifetime, and the proposed SI_KERNEL payload. They also require a material correction: Linux rearms periodic ITIMER_REAL on shared SIGALRM **dequeue**, not on timer expiry or queue acceptance. The frozen proposal's instruction to preserve f615's immediate rearm is not sufficient for Linux-equivalent blocked/delayed behavior.

This addendum is separate from unchanged `REPORT.md` (SHA256 `a96f4cc34d5eed3123135b8c93b0f2d7855694c4d5e853fd9c64dd299b29f85f`) and `DELIVERY_PROPOSAL.md` (`6e8526b1c29053885e71e1f580aaa17d50b22472360160cf41a8da16a3c9d5e9`). It records corrections and remaining implementation/design obligations, not a patched proposal or executed test result. Hermit remains f615 / Reverie 7d as bound in the original manifest.

## Corrections established by primary source

### C1. Queue acceptance is not periodic-timer consumption

At upstream Linux v7.1.3 commit `199c9959d3a9b53f346c221757fc7ac507fbac50`, `kernel/time/itimer.c:180` (`it_real_fn`) sends SIGALRM to the TGID and returns `HRTIMER_NORESTART`. `kernel/signal.c:629–636` first dequeues a private signal; if none is available, it dequeues from the process-shared queue and calls `posixtimer_rearm_itimer` for shared SIGALRM. `itimer.c:160–172` rearms only when the real timer is not queued and its current interval is nonzero. `hrtimer_forward` (`kernel/time/hrtimer.c:1061`) forwards the original expiry by enough whole periods to place it strictly beyond the current time.

This differs from f615 `TimedEvents::pop_if_before`, which immediately inserts `old_deadline + interval` at every expiry. Concrete distinguishing sequence, expressed in the same clock units: initial deadline 10, interval 10, SIGALRM blocked through time 35. Linux expires once, retains a pending standard signal, and leaves the real timer inactive until consumption. Before unblocking, `getitimer` sees remaining value 0 and interval 10. On shared dequeue at 35, the next expiry becomes 40. F615 instead keeps popping deadlines 20 and 30 and reports time remaining to another armed deadline; its separate existing getitimer interval-zero bug further differs. Coalescing the guest handler count does not make these timer-state observations or extra producer events equivalent.

**Concrete correction owed:** retain timer arming state separately from process-pending signal state. A successful expiry publishes/coalesces pending SIGALRM and makes the real timer inactive while retaining its periodic interval and phase. Add a causal notification of an **actual shared SIGALRM dequeue**, then rearm at `d + (floor((now-d)/p)+1)*p` for `now >= d`, only if the current real timer is inactive and its current interval is nonzero. This is arithmetic on the existing continuous logical clock, not permission to round, freeze, reset, widen margins, or invent elapsed time. The timer's current arm/version and actual process lifetime must be checked: disarm prevents rearm; a replacement arm that is already active must not be overwritten by consuming an older pending signal.

The notification is not “handler completed” or “a timer-origin event was queued.” Linux rearms before ptrace filtering and before deciding which handler/disposition applies (`signal.c:2918` onward). It also rearms on **any** shared SIGALRM dequeue while the real timer is inactive/periodic, not only a siginfo whose producer was the timer. For example, an earlier blocked software SIGALRM may retain its first siginfo when the timer expiry coalesces into it; consuming that shared signal still rearms the timer. Conversely, private/thread-directed SIGALRM does not take this rearm branch.

The consuming paths include handler selection, `sigtimedwait` (`signal.c:3770`, `:3789`) and `signalfd` (`fs/signalfd.c:162`, `:177`), all using `dequeue_signal`. A handler-only callback would miss real consumption by those APIs. No handler should be fabricated for a signalfd read. The new queue receipt proposed in the frozen text remains useful for publication/wake safety, but cannot stand in for this distinct consumption event. A concrete callback/RPC integration covering the supported consumption sites remains to be designed and independently reviewed; this addendum does not invent an approved interface.

The pinned KVM consumers make the missing boundary concrete. `executor.rs:3122` retains `PendingSignalDomain` for handler delivery, but `take_signalfd_event` (`:7114`) and `rt_sigtimedwait` (`:13648`) currently erase the private/process distinction before returning an event. All three can encounter readiness or copyout errors after removing pending state. The consumption notice must retain that domain and occur at actual removal, even if a later step fails. Linux likewise dequeues/rearms before signalfd copyout (`fs/signalfd.c:216–221`) and before sigtimedwait siginfo copyout (`signal.c:3828–3832`); successful syscall return is not the required trigger. This confirms the native reviewer's additional source finding without claiming those paths have been changed.

### C2. Ignored Tool observation must not finish the guest wait

POSIX.1-2024 §2.4.4 states that ignored signals must not affect a function's behavior and blocked signals must not affect it until unblocked/delivered, apart from pending/signal-wait queries. Linux agrees, but a tracer can still observe an ignored signal: `sig_ignored` (`signal.c:106`) preserves blocked signals and permits ptrace observation of ignored signals; `get_signal` dequeues/rearms before the ptrace hook, then continues past SIG_IGN (`:2918–2941`). When no handler is delivered, x86 `arch_do_signal_or_restart` (`arch/x86/kernel/signal.c:333–365`) restarts internal restart results rather than returning an invented EINTR.

The frozen proposal correctly rejects an ignored-signal wake as guest EINTR. Its suggestion to leave every unblocked ignored signal pending until the ordinary syscall callback finishes, however, does **not** establish ptrace-equivalent Tool-observation or periodic-rearm timing. A long sleep can legitimately continue after a tracer-only observation; a pause may never finish, while its ignored signal was still observed and consumed by the tracer path. Delaying consumption until syscall completion is not justified by the “no effect on the guest function” rule.

**Concrete correction owed:** separate service of a real pending signal/Tool observation from authorization to finish the original wait. For ignored or suppressed delivery, retain the same absolute sleep deadline and no user-visible EINTR; for caught delivery, use the actual syscall-specific interruption/restart result. The owned callback/continuation design must show how that service occurs without recursively granting ordinary guest work, losing the original Resources, deadlocking the scheduler, or synthesizing an unused hook. A queue receipt alone does not establish it. The native reviewer is independently evaluating this transport boundary.

Blocked+ignored also needs its own case. POSIX §2.4.1 permits either immediate discard or retention when a signal is already ignored and blocked at generation. Linux's `sig_ignored` explicitly retains it because the disposition may change before unblocking. **Setting** the disposition to SIG_IGN after a signal is pending instead discards old pending instances, blocked or not (`do_sigaction`, `signal.c:4344–4364`; POSIX §2.4.3). The proposal's generation handling must preserve this distinction. SIGCHLD's special parent-notification suppression is not a universal signal rule.

For an untraced, unblocked SIG_IGN case, this upstream code can reject generation in `prepare_signal` and consequently has no queued SIGALRM to trigger the periodic rearm path. That is a source-path consequence, not a measured claim about this vendor kernel. The Tool/ptrace observation contract must be explicit; substituting the untraced path to erase real INFO observations is not proposed.

### C3. getitimer must expose the actual timer state

Linux `do_getitimer` (`itimer.c:76–96`) returns both remaining time and `it_real_incr`. The man page and historical POSIX specification require the current interval as well. F615 `handle_getitimer` always writes interval zero. This was identified separately in the frozen diagnosis and is not the cause of the sandbox death, but the new periodic-state controls must assert the real interval and inactive-pending state rather than adopting that existing bug as the oracle. Correcting delivery does not automatically correct this API.

## Confirmed contract and its exact evidence

| Question | Primary result and consequence for the finite correction |
| --- | --- |
| Direction and recipient | ITIMER_REAL is process-wide. `it_real_fn` uses the signal group's TGID; `kill_pid_info` (`signal.c:1470`) selects `PIDTYPE_TGID`; `__send_signal_locked` uses `shared_pending` for that type (`:1054`). POSIX §2.4.1 and signal(7) permit one eligible unblocked thread/signal waiter. The creator TID is not a permanent recipient. Current single-live-thread support is an explicit finite implementation limit, not a changed product requirement. |
| Standard coalescing | `legacy_queue` (`signal.c:1035`) returns early for an already pending non-RT signal before overwriting siginfo. signal(7) explicitly retains first siginfo. Preserve complete first metadata and process/private domain; do not count one handler per periodic deadline while the signal is pending. POSIX leaves multiplicity implementation-defined outside mandatory queueing; Linux supplies the concrete target behavior here. |
| Disarm versus pending | `do_setitimer` (`itimer.c:237–274`) cancels the active hrtimer and sets interval zero for value zero; it does not remove pending SIGALRM. A blocked alarm generated before disarm remains pending and may later be accepted/delivered once; its consumption must not rearm the disarmed timer. A repeated SIG_IGN disposition operation is different because it flushes pending state. |
| Fork | Linux `copy_signal` (`kernel/fork.c:1696–1734`) allocates zeroed new process signal/timer state and initializes an unarmed real timer; child private pending state is separately initialized at `:2155`. signal(7) confirms inherited dispositions/mask but empty pending set; setitimer(2) confirms no inherited interval timers. CLONE_THREAD shares process signal state and is a different case. |
| Exec | setitimer(2) confirms interval timers survive exec. signal(7) confirms masks/pending survive, caught handlers reset, ignored dispositions remain. Reused `fs/exec.c:1160–1163` calls `exit_itimers` and `flush_itimer_signals`, but these refer to POSIX timer objects and SI_TIMER: `posix-timers.c:1070` walks `posix_timers`; `signal.c:1899–1928` preserves non-SI_TIMER pending entries. `flush_signal_handlers` (`signal.c:520`) preserves SIG_IGN and resets caught handlers. Do not clear pending SI_KERNEL ALRM or the process interval solely because MmId changes. |
| siginfo | `it_real_fn` uses SEND_SIG_PRIV; `signal.c:1103–1109` clears siginfo then sets signo, errno=0, code=SI_KERNEL, pid=uid=0. `copy_siginfo_to_user` (`:3502`) zeroes expansion bytes. `SI_KERNEL` is 0x80, distinct from `SI_TIMER=-2` (`include/uapi/asm-generic/siginfo.h:175–177`). Thus the proposed zero-filled 128-byte normal ALRM payload with coherent signo/SI_KERNEL is supported. Kernel allocation-failure fallback can lose metadata; no such failure was measured, and it need not be fabricated in a normal successful virtual event. |
| Sleep and pause interruption | nanosleep(2) ends for elapsed duration, caught delivery, or termination; caught delivery returns EINTR and relative remaining time. signal(7) lists nanosleep/clock_nanosleep/usleep/pause among interfaces not restarted after a handler even with SA_RESTART. Kernel hrtimer code saves an absolute restart expiry, with `ERESTART_RESTARTBLOCK`/`ERESTARTNOHAND` (`hrtimer.c:2284–2352`); x86 converts those to EINTR when delivering a handler (`arch/x86/kernel/signal.c:267`). A blocked/ignored event alone is not a successful interruption. |
| Other syscall families | signal(7) distinguishes restartable slow read/write, wait and futex operations from nonrestartable waits. Partial transferred data returns its successful count. x86 only makes ERESTARTSYS conditional on SA_RESTART; other internal restart classes have different rules. Do not turn every retained Resources value into generic EINTR or enable KVM's currently false parked-write-interruption capability without implementing/qualifying it. |
| Handler mask and return | sigaction(2) and signal(7) require adding sa_mask plus the delivered signal unless SA_NODEFER, SA_RESETHAND at handler entry, and saved pre-handler context/mask restored by sigreturn. The pinned VM/executor frame path already implements these mechanisms; its actual execution still requires qualification. |
| Fatal default | POSIX §2.4.3 requires signal termination, including a signal wait status, rather than a normal numeric exit. Reverie 7d `force_signal_exit` calls `terminating_signal_status` (`executor.rs:3367`, `:13479`), which produces `ExitStatus::Signaled`; only the conventional CLI rendering maps that to 128+signal. The new control must check actual typed/child signal status and reporter survival, not accept any nonzero exit as evidence of correct default action. |

The historical POSIX setitimer page is Issue 7 / IEEE 1003.1-2017, where the interface is obsolescent. POSIX.1-2024 removed setitimer; current general signal rules remain relevant. This distinction prevents claiming the old XSI entry is a current Issue 8 API. The Linux man pages fetched identify man-pages 6.19. No host-specific tolerance or clock quantization is imported from these references.

## Transport corrections received during this follow-up

The independent native reviewer identified two additional concrete points, confirmed here against the already-bound f615 sources. These are code-ownership corrections, not conclusions supplied by the Linux references.

- `recv_request_resources` is reached by direct `RequestResources` (`tool_global.rs:995`), a nested ParentContinue (`:1760`) and TraceSchedEvent (`:2209`). FutexAction separately awaits/matches SchedResponse (`:2014`); thread-start even discards its response (`:1854`). A filled request Ivar does not prove the caller will recognize an alarm-control response. **Correction:** admission needs an explicit control-capable origin/transport witness bound to the exact req/resp Ivar and current mm. Nested/independent callers must either be implemented with that protocol or explicitly lack the capability; they must never receive a control that is mistaken for an ordinary grant or ignored. The original fixture's direct SleepUntil path remains a positive obligation, not an excuse to skip other declared cases.
- The warning above `do_a_turn_blocking` about a duplicated nonblocking `step` is stale in this target. Actual f615 has one production caller of `step2_process_blocked` at scheduler.rs:1308; other direct calls are tests. **Correction:** the proposal should cover that real production entry, both timed-event branches, and relevant direct test seams. There is no second established public entry to invent or implement merely because a comment mentions it.

## Required finite controls and remaining obligations

Keep the original setitimer verification cell and all existing comparison/count/time limits unchanged. The reference corrections add concrete nearby controls; none has run:

1. Block a periodic ALRM beyond multiple intervals; assert no guest EINTR, one process-pending signal, correct nonzero interval with inactive remaining value, then one delivery and the next expiry at the original phase strictly after actual consumption. A model-level exact clock test should pair with a real initialized-VM guest; no widened native timing window is a substitute for deterministic evidence.
2. Generate while blocked, disarm, then consume/unblock: one retained event and no rearm. Replace the arm while an older event is pending: consuming it cannot overwrite the replacement's active deadline. Coalesce a first software/process ALRM with an expiry and retain first siginfo while rearming from actual shared dequeue; a private ALRM is the negative domain control.
3. Exercise actual signalfd and sigtimedwait consumption where supported; require no guest handler, correct payload and periodic continuation. Do not report these APIs supported from readiness-only tests. Any remaining unsupported consumer must remain a visible failure, not an inventory exemption.
4. Observe ignored/suppressed signals through the real Tool while a finite wait continues to its original deadline; assert no EINTR and distinguish the real signal observation from sleep completion. Pair with caught ALRM under both SA_RESTART settings for nanosleep/pause, and retain separate syscall-specific restart/partial-data controls before extending beyond SleepUntil.
5. Fork preserves the parent's timer/pending state but gives the child neither; exec retains timer/pending/mask while caught action resets. Test blocked pending ALRM through exec followed by a newly installed handler and unblock, plus the default-fatal counterpart with typed signal status and surviving reporter. Preserve mask/SA_NODEFER/SA_RESETHAND/rt_sigreturn controls.
6. Transport controls must exercise direct versus nested/unaware RPC origins, exact Ivar/mm reuse and terminal cancellation around acceptance and consumption. Queue receipt, dequeue notice, and completed handler are separate observations; no fabricated receipt or successful summary may substitute for any of them.
