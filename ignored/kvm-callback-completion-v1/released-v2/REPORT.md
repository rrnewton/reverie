Callback completion driver, released private source

The production drive_handler_completion now returns CaughtFuture<HandlerOutcome<T>>, retaining the selected outcome separately from polling and destruction. This source is uncompiled. Root owns all production call-site changes, final owner handling, the new test-module declaration, formatting and execution. This report is an implementation account, not independent approval or evidence that the complete originating-error path is fixed.

The polling driver owns only borrows of two separate pinned allocations: the callback and the failure future. It stores selected HandlerOutcome in an Option outside the caught poll_fn, which returns only unit. Thus destroying a discarded Ready callback value cannot erase an already selected RuntimeError while polling unwinds. catch_owned_future ends polling after Ready or panic. If polling panicked before selection, the driver takes the still-owned HandlerSignal, recovering even a poisoned signal mutex; a stored RuntimeError and its exact error tree remain available before callback destruction. Other stored signal variants preserve their corresponding owned outcome rather than being silently dropped on that panic path.

Callback destruction then runs in its own catch with the outcome outside it. Failure-future destruction follows in a separate catch, preserving the original callback-before-failure destruction order and preventing that destructor from discarding the selected error. Payload Boxes are retained without stringification or reboxing, in polling/driver, callback-destruction, then failure-future-destruction order. A failed poll is never repeated. No publication, panic propagation, owner acknowledgement, effect settlement or new child start runs after the caught terminal/panic decision in this driver.

Normal ordering is preserved: check failure before polling the callback, check failure again after it, prefer a recorded handler signal over a returned value or ordinary suspension, and start registered children only on an otherwise ordinary Pending callback. The original RuntimeError still outranks a bare failure cancellation. Existing partial child-start behavior and errors are unchanged. The production API adds no public bounds. Its inferred auto traits and the composed callers still require compilation; none is claimed from these static bytes.

The original name drive_handler remains only as a cfg(test) wrapper for the pre-existing non-panicking controls. It awaits production completion, resumes the first original payload when present, and otherwise returns the outcome. That compatibility wrapper does not establish preservation of outcomes/secondary payloads through its own resumed unwind and must not be used as the production ownership route.

Five new finite host controls call the production completion function directly:

- owned_runtime_error_survives_actual_callback_destructor_panic retains the unique strong error owner when actual callback Drop panics, and preserves that exact original payload Box.
- owned_runtime_error_survives_normal_callback_destruction is the non-panicking neighbor. It checks that a simultaneously ready failure cannot replace the stored error with RunFailed.
- polling_panic_recovers_owned_error_before_callback_destructor_panic deliberately panics while holding the real signal mutex after transferring its only strong error owner. It requires recovery from poison, actual callback destruction, no repoll, and both original payloads in order.
- owned_runtime_error_survives_failure_future_destructor_panic checks the separate failure-future destruction edge after normal callback destruction.
- selected_runtime_error_survives_discarded_ready_value_panic covers an already selected RuntimeError while the discarded Ready callback value's destructor panics before the polling driver returns.

The error tests retain only Weak outside the actual signal/outcome route. The unique Arc and complete constructed SignalEffects value survive: two distinct removals, partial acknowledgement watermark, FailedAfterCommit publication receipt, raw EFAULT result, original context allocation and fields, and nested HostIo(EAGAIN)/GuestClock cleanup causes. These are constructed typed ledgers, not a test of real signal queue removal/publication. Exact payload allocation identity, exactly-once poll/destruction, no extra error owner, and unresolved child-start gate are checked. Dropping the returned completion releases the final strong error owner.

An initial source-only draft is preserved in the parent directory. Before sealing, static inspection identified the discarded-Ready-value edge and led to this explicit successor and fifth control. No baseline or candidate test was executed. Do not infer a measured failure/pass from that correction.

No existing test, assertion, tolerance, comparator, exemption, skip or failure label was weakened or deleted. No compiler, formatter, product run, test, model, network or SCM operation was performed. Arbitrary external cancellation still has ordinary future-drop behavior; Rust abort from a double panic during already-unwinding destruction is not recoverable here.
