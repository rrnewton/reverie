Background: the KVM executor keeps one authoritative descriptor table shared by CLONE_FILES workers and a private snapshot in each executor. An epoll registration now records a logical binding from one originating table. A normal fork must copy a coherent table snapshot into fresh child bindings; a close in another worker must not be mistaken for the death of every already-forked copy.

## Actual production call and lock basis

1. executor.rs execute_checked_inner (around 6548-6602) locks self.file_table, calls FileTableState::install into self.state, and handles any failed clone before preparing the process action. Install (around 3020-3095) copies the Files/entry IDs and the domain, poll table identity and native binding map from the same authoritative table while that mutex is held. That is the coherent descriptor-snapshot point for the issued guest fork.
2. fork/vfork/process clone are not in mutates_file_table (around 3098-3149). The table guard is therefore released before execute_process_action -> prepare_fork (around 3330-3550), which publishes ProcessAction::Fork. There is no claim that the table lock stays held until the child starts.
3. Direct execution collects the action after execute_static_elf_syscall (vm.rs around 4856-4875) and runs it through run_process_action_at_boundary -> run_process_action_inner. Tool injection collects it in runtime.rs complete_injection (around 969) and calls the Tool process-action path; the ordinary Tool loop has its corresponding path around runtime.rs 5850-5895. Both fork arms converge on vm.rs prepare_forked_process_admitted (around 2450-2468), whose first step is executor.fork_child(...).
4. fork_child (executor.rs around 3637-3680) takes the source signal_transaction and retirement scope, checks signalfd policy, and calls self.state.try_clone_for_fork_locked. It does NOT acquire self.file_table or install a newer authoritative state. The elf helper (elf.rs around 972-1085) clones that executor's retained Files, clones the native description references, creates a new NativePollTable via fork_identity, and creates a new NativePollBinding for each logical child entry. fork_child then publishes a new private FileTableState from the resulting child state.
5. The source signal transaction protects the existing process/signal-copy protocol; it is not the authority-table mutex. The coherent Files/bindings snapshot comes from step 1. A newly live child binding is justified by copying a descriptor that was present at that snapshot, not by the old binding's current live bit.

## Why a later parent close does not make every copied child binding false

A sibling close may occur after step 1 and before the fork helper. The invoking executor retains the old File and metadata; its old binding may be marked dead for the shared parent table. Cloning the retained File into a fresh child binding still represents a fork linearized at step 1, before the overlapping close. The child's table is private and its lifetime must be independent of subsequent closes in the parent. Checking the parent token's later live bit and refusing every such copy would confuse two table lifetimes.

This does not mean the helper always sees the latest table at its own call time, nor does it assert that every runtime/scheduler interleaving has been formally reviewed. It says the production guest-fork path has a concrete earlier snapshot inside that syscall's interval. Inherited old epolls remain outside immediate-wait admission because their records name the parent table; a fresh epoll created in the child can use the child's fresh proven bindings, subject to the unsafe-history rule below.

## Unsupported UNSHARE history is not erased

close_range (executor.rs around 16568-16602) validates low-word bounds/flags, then, for CLOSE_RANGE_UNSHARE, takes the epoll domain and sets state.poll_table_id.unsafe_history = true before changing CLOEXEC state or closing entries. It does not pretend to implement Linux's per-caller table split. close_range is a file-table-mutating dispatcher call, so its authoritative descriptor/CLOEXEC changes publish under the table mutex. The unsafe marker itself is shared by every CLONE_FILES snapshot of that table.

NativePollTable::fork_identity (around 2066-2073) creates a new table identity while copying that sticky flag with a SeqCst atomic load. EpollProof::admitted (around 2152-2165) tests the current table's flag in addition to record-specific history and exact origin identity. Therefore a fork after an already-recorded UNSHARE carries the unsupported history, and creating a new child epoll cannot manufacture a clean proof. Exec preserves the previous table identity. CLONE_FILES construction explicitly replaces the temporary fork identity with the parent's shared table Arc and binding Arcs (around 3810-3814), so it cannot reset the flag either.

A concurrent UNSHARE before the flag load can conservatively taint a child whose descriptor snapshot preceded that operation. If UNSHARE happens after the fork's flag load, the clean private child can still be associated with the earlier clean snapshot. Neither outcome silently treats an already-known unsupported split as repaired. This reasoning concerns admission only; close_range's existing process-wide approximation remains a Linux parity limitation.

## The concrete prerequisite and its current boundary

fork_child is NOT a standalone authoritative-snapshot API: its &self implementation copies local state. Any new production caller that invokes it after an unrelated sibling mutation without first obtaining the invoking executor's coherent snapshot could copy a stale descriptor table and mint fresh live tokens for it. Merely pointing to signal_transaction, a new Arc or fork_identity would not establish correctness for that caller.

The inspected production caller is reached from the installed guest-fork snapshot as above, so this trace found no additional missing prerequisite in the current UNSHARE inheritance change. Keep that caller precondition explicit. Direct unit calls to fork_child do not establish it automatically and should not be presented as an end-to-end guest-fork concurrency proof. If future call paths break that sequencing, they need an authoritative snapshot under file_table or a prepared snapshot object bound to ProcessAction::Fork; that is a concrete requirement for those paths, not a requested redesign in this task.
