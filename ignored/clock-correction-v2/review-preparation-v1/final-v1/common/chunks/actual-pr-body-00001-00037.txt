## Plain Language Summary and Project Impact

Ptrace setup and syscall injection were adding work to the guest's branch clock. A retained trace showed setup executing the guest's first branch and restoring its instruction pointer, making that branch run again. An injection at the wrong stop could also repeat guest memory effects.

Distinguish an actual pending syscall from other stopped states, and clear consumed syscall state before subsequent callbacks. Start an initial command's branch counter at successful exec while retaining existing behavior for function guests and later execs. This repairs the ptrace reference used for same-run backend parity without adding an offset or reducing clock precision.

## Determinism

Only a real pending, different syscall takes the syscall-suppression step. Injection at a post-exec or instruction callback uses the private syscall path directly, leaving the guest instruction and memory untouched. Same-call and tail injection retain their existing execution paths. Successful exec clears obsolete syscall state.

The initial-command counter becomes active at the actual exec boundary, before guest execution. Startup notification requests retire at that boundary; new post-exec timers remain active. Exact guest branch trajectories remain 1/65 and 65/129. There is no fixed subtraction, repeated-exec reset, rounding or comparison filtering.

## Linux Semantics

Injecting a syscall must not execute and rewind an unrelated guest instruction. Regressions exercise original and replacement writes, exact return values including EBADF and EPERM, a nonreturning injected exit, and emulated returns followed by an RDTSC callback. The existing legacy-vsyscall test reached actual time interception and its return-value and memory assertions.

## Relationship to gVisor

This change repairs ptrace execution and clock accounting; it does not add a KVM syscall implementation. Hermit's KVM backend needs a faithful ptrace reference for same-run parity. No gVisor API or implementation is introduced.
