## What I checked and judge sound

- **Provenance isolation.** `command_bootstrap` is set true at exactly one site (`tracer.rs:2506`, the Command `spawn`), false at `tracer.rs:2658` (`spawn_fn`), `task.rs:1226` (`cloned`), `task.rs:1284` (`forked`). It is cleared at `task.rs:2874`, the first statement of `handle_exec_event`, before any post-exec Tool callback. The design's requirement to read the private state *before* that clear is correctly placed. `TracerBuilder` exposes only Command spawn and function spawn — there is no attach-existing-process constructor, and GDB attaches to an already-constructed `TracedTask`. The design invents no attach support.
- **Which instructions count.** The 223 are user-mode (`exclude_kernel(1)`, `perf.rs`) launcher branches after `traceme_and_stop()` inside `init_tracee` (`tracer.rs`, the pre_exec callback) — the remainder of `Container::setup`, the seccomp filter load, and `libc::execvpe`. `container.rs` runs pre_exec callbacks *before* installing the filter, exactly as the design states; I verified that ordering and the accompanying comment directly. The design's refusal to split those contributions further is honest.
- **One-shot activation.** `event_enable_on_exec` clears `attr.enable_on_exec` unconditionally at `core.c:4673` before deciding, so later execs are inert with no further tracer action. The design's "this transition occurs once" is guaranteed by the kernel, not just by convention.
- **Child constructors.** Both child paths construct a fresh immediate `Timer`; the design's prohibition on making a child wait for its own future exec is correct — a child that branches before exec must count those branches.
- **Unsupported PMU.** `Timer::new` leaves `inner: None`; `read_clock` would panic through `inner()`. The design's "preserve current refusal/capability semantics, no zero-clock fallback" is right, and the implementer must use `inner_noinit`/`inner_mut_noinit`.
- **`generated_signal` aliasing.** The design's step 2 caution is precisely correct and I verified why: `timer.rs:802-812` returns true for *any* `MARKER_SIGNAL` when `send_artificial_signal` is set, with no fd check. Keeping the "artificial send happened" fact separate from "a short request is pending" is load-bearing, and PLAN control 1 must assert it rather than assume it.
- **aarch64 / LiteInst.** Correctly unclaimed; `PmuConfig::new()` on aarch64 assumes BR_RETIRED with skid 1000 and `has_precise_ip()` returns true unconditionally, so parity there would need its own evidence.

# Determinism

**Sound, and I can state the proof from source rather than from the design's summary.**

Detcore consumes the Reverie clock only as a **delta**: `update_logical_time_rcbs` (`detcore/src/lib.rs`) reads `guest.read_clock()`, asserts `committed_clock_value <= clock_value`, computes `delta_rcbs = clock_value - committed_clock_value`, charges that into `thread_logical_time`, and stores `committed_clock_value = clock_value`. `committed_clock_value` starts at 0. Timer requests are relative (`post_handler_hook` computes `rcbs_remaining` and calls `set_timer_precise(Rcbs(rcbs_remaining))`) and `TimerImpl::request_event` converts them to an absolute target in the *same* counter (`clock = self.read_clock() + delivery`, `timer.rs:785`).

Therefore:
1. Moving the origin changes exactly one quantity — the first delta, from 223 to 0. Every subsequent delta is a difference and is untouched. That matches the measurement exactly: the cross-backend offset is a **constant** 2,230 ns from turn 2 through turn 16, and the final totals differ by 9,112,750 − 9,110,520 = 2,230.
2. Timer coordinates stay internally consistent because both the request and the target live in the same counter.
3. The origin is fixed by a **guest-causal** kernel event — the guest's own successful `execve` — not by host timing. `perf_event_exec()` runs at a fixed point inside `begin_new_exec`, the same point on every run.
4. The `committed_clock_value <= clock_value` assertion cannot be broken: both start at 0 and the counter only counts up; `enable_on_exec` starts counting, it never resets.
5. Nothing is rounded, frozen, reset, coarsened or compensated. `Guest::read_clock`'s documented contract at `reverie/src/guest.rs:420-423` already declares the starting value implementation-specific, so the change is inside the contract. Against `continuous-virtual-time-is-sacred`, removing launcher work from guest virtual time is a fidelity *improvement*: it makes the guest's clock measure the guest.

The only behavioural change for a long-running guest is that its first timeslice gains 223 RCBs (0.001115% of the 20,000,000 target) — deterministically, and in the correct direction.

Residual host-timed input: PMU skid on the *sampling* event, unchanged by this design.

# Linux / POSIX semantics

No guest-visible Linux interface changes. `read_clock` is a Reverie-internal clock with no POSIX counterpart, and its starting value is documented as implementation-specific. The exec paths are respected rather than reinterpreted: pre-commit failure returns to the old image with no activation; post-commit failure is fatal by construction (`bprm->point_of_no_return = true`, `fs/exec.c:1112`); `PTRACE_EVENT_EXEC` is reported only on success (`fs/exec.c:1719`). `init_tracee`'s documented loss of `execve` error reporting (the fd 3..256 close) is acknowledged, not papered over, and the design explicitly declines to claim a repair for it.

The one semantic change is the timer-delivery difference in **F1**: a start-time request that today produces a (premature, launcher-context) `handle_timer_event` would produce no callback. That is permitted by `Guest::set_timer`'s cancellation rule, but it must be *stated*, and the negative observation must be preserved rather than left to "record whether".

# Evidence and goalpost-moving

## Assessment of all four targets

**1. Weakening an assertion so a test passes — NO.** No assertion is changed. Three existing tests are named for retention: `command_bootstrap_ends_before_post_exec_and_later_guest_exec`, `spawn_fn_never_has_command_bootstrap_provenance`, `precise_timer_delivery_reaches_tool`. The one clause that *could* hide a weakening is PLAN control 5's "Do not require delivery of a request which the documented event-cancellation rule cancels." **2.
